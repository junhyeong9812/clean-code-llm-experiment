## 1. 질문과 가설

- **질문:** 사람이 읽기 좋은 구조(레이어·캡슐화·도메인 모델)는 LLM 코딩 에이전트의 **탐색 비용**과 **정답률**에도 도움이 되는가?
- **처치(독립 변수):** 코드 구조 — `god`(절차 전체가 `Marketplace.kt` 1개, 2,692줄 중 1,772줄) vs `layered`(`api·service·domain·infra` 54파일, 4,756줄, 최대 파일 535줄). 동작·SQL은 같다(행동 테스트 211개·equiv 12개 시나리오 — 응답·DB·Hibernate SQL·DB 문장 로그 같음).
- **가설(사전 등록):** layered에서 같은 과제의 총 토큰이 적고(÷god 비 < 0.8이면 효과, 0.8~1 미미, ≥ 1 손해 — 앞 실험과 같은 기준), 정답률은 같거나 높다.
- **기준(B):** god. 모든 비율은 **layered ÷ god**.

- 1차 결론은 "Sonnet · 수정 과제 · 이 코드 크기에서"로 한정해 보고한다(§9 위협 1·6·11).
- **추정 대상이 다르다:** 1차 기하평균은 수정 과제 6개 위의 값이다. 사전 등록 요약(질문 과제 토큰 포함 8과제)과 같은 추정 대상이 아니다. 질문 과제는 god에 유리할 것으로 미리 표시된 과제(Q1 — god KDoc `:1626-1633`이 답을 요약)라서, 빼면 요약이 layered 쪽으로 치우칠 수 있다. README 결론에도 이 범위를 함께 쓴다(§7의 5).
- **1차 결론은 그 범위에서 최종이다.** 뒤에 재개하는 실행(Haiku·Opus·Q1·Q2)은 별도 사전 등록 단위로 보고하고 1차 표본과 합치지 않는다(모델 ID·CLI 버전·실행 시점이 달라지므로 — 위협 10).
- **크기 재측정 조건:** 1차 판정이 '미미'이거나 '불확실' 꼬리표가 붙으면 "크기를 키운 재측정"을 다음 결정 후보로 올린다(위 첫 문단의 "차이 없음"을 이렇게 읽는다).

- 규모는 지금 코드 크기로 먼저 잰다(ADR-0001의 "구현당 1만 줄" 목표 미달 — §9 위협 1). 결과가 "차이 없음"이면 크기를 키운 재측정을 다음 결정으로 남긴다.
- 비용은 구독 범위 안에서 쓴다. 실행마다 `total_cost_usd`(명목)·토큰을 기록해 파일럿 뒤와 모델마다 보고한다. 사용량 한도에 걸린 실행은 무효(§6.4)로 다시 돈다.

## 3. 과제

### 3.1 원칙

- **구조 중립:** 과제 문장(TASK.md)·공개 테스트·숨은 테스트는 두 구조가 같다. 테스트는 HTTP·DB 수준(`behavior-tests`와 같은 방식 — 앱 jar + 1k 시드 DB + 가짜 PG)이라 내부 타입·패키지를 모른다.
- **주입은 같은 의미로:** 결함·변경 지점은 두 구조에서 같은 규칙을 같은 방식으로 깨거나 바꾼다. 구조별 정답 패치(`fix.god.patch`·`fix.layered.patch`)를 따로 둔다 — 차이는 고칠 곳의 위치·개수뿐이어야 한다.
- **누출 금지:** TASK.md는 증상·기대 동작·재현 방법만. 원인 위치(파일·클래스·함수 이름)는 쓰지 않는다. 에이전트 사본에서 기존 계약 테스트는 뺀다(주입된 결함을 이름·기대값으로 드러내므로 — 앞 실험 교훈).
- **같은 축 2개 이상:** 유형마다 2개 — 결론이 과제 하나에 몰리지 않게(앞 실험 교훈: 정답률 차이가 과제 05 하나에 몰림).
- **판정 결정성:** 숨은 테스트는 주입 상태에서 실패, 정답 패치(두 구조 각각)에서 5회 반복 전부 통과해야 채택. 숨은 테스트가 요구하는 경로가 두 구조 모두에서 실제 호출되는지 확인한다(앞 실험 과제 05: 죽은 경로를 요구해 정확히 읽은 쪽이 감점). T1·P2처럼 기존 계약 테스트가 주입을 못 잡는 과제는 숨은 테스트가 유일한 판정이다. **채택 조건에 "design.md의 순진한 오답 패치마다 숨은 테스트가 실패"를 포함한다**(오답이 success로 세지 않게 — 예: P1의 금액 비교 삭제·매번 새 키, P2의 상태만 UNKNOWN으로 바꾸고 APPROVE UNKNOWN 행을 쓰지 않기).
- **숨은 테스트는 결과를 단언한다:** 구현 방식(키 형식·쿼리 모양)을 단언하지 않는다 — 대안 정답이 통과해야 한다(예: P1은 가짜 PG `/_control/cancellations`에서 항목마다 서로 다른 취소 기록과 각 금액, 같은 항목 재요청이 새 기록을 만들지 않음을 보고 키 문자열은 보지 않는다. P2는 APPROVE UNKNOWN 행과 pg-inquiry 뒤 PAID 전환까지 본다).
- **고칠 곳의 수를 맞춘다:** 주입·정답 diff는 두 구조에서 같은 수의 지점이어야 한다(구조가 원래 다르게 나뉜 과제 — C2 — 는 예외로 표시). 선검증 표 §3.2.
- **주석:** 주입·변경되는 **규칙을 서술한 주석은 저장소 전체에서(grep) 두 구조 모두 지운다**(사용자 결정 2026-10-25) — "근처"만 지우면 layered에 서술이 여러 곳 남는다(T1: `domain/Point.kt:35·288`, `service/PointBook.kt:21` / P1: `domain/PaymentGateway.kt:59`, `domain/Order.kt:500`). 지운 곳과 남는 올바른 구현 잔여물(예: P1 god `:1031` 리터럴, layered `keyFor`)의 구조별 개수를 design.md에 적는다.

### 5.2 기전 지표 (구조 차이가 왜 생기는지)

- **관련 심볼 첫 겨냥 턴:** oracle의 `symbols.<구조>.txt`(고칠 곳·읽어야 할 곳의 함수·줄 범위)에 대해, 그 범위를 **겨냥한** 첫 접근이 나온 턴. 앞 실험의 "파일 이름이 입력에 처음 나온 턴"은 쓰지 않는다. 겨냥의 정의 *(개정 1 — 러너 `events.targeted`)*:
  - **Read:** offset을 준 Read가 돌려받은 범위가 span을 **전부 덮고**, 그 폭이 **400줄 이하**(사용자 결정 2026-10-26). 범위는 이벤트의 구조화 결과(`tool_use_result.file.startLine·numLines`)로 정한다. 구조화 결과가 없으면 결과 텍스트의 줄 번호(첫 번호가 offset과 같을 때만), 그것도 없으면 입력 offset·limit(요청 폭)으로 정한다.
  - **청크 읽기:** offset이 있어도 폭이 400줄을 넘으면 겨냥이 아니고 "청크 읽기 턴"으로 따로 기록한다. god의 큰 파일을 나눠 읽기만 해도 포화되는 것을 막기 위해서다(layered는 파일이 작아 구조에 비대칭으로 걸린다).
  - **전체 읽기:** offset 없는 Read, 파일 전체를 돌려받은 Read, Bash `cat 파일`은 "전체 읽기 턴"으로 따로 기록한다(god `Marketplace.kt` 1,772줄은 기본 상한 2,000줄 안이라 전체 Read 1회로 포화되므로).
  - **검색 결과:** 검색 결과의 줄이 span 안이면 겨냥이다. CLI 2.1.308에는 Grep 도구가 없어 에이전트가 Bash `grep -n`을 쓰므로 Bash `grep`·`rg`의 줄 번호 출력도 같은 규칙으로 센다(스모크 실측).
  - **Bash 범위 읽기(`sed -n 'A,Bp'`):** Read와 같은 규칙 — span을 전부 덮고 폭 ≤ 400이면 겨냥, 더 넓으면 청크 읽기로 따로 기록한다. *(과제 A 작업에서 반영 — 그 전 러너 `3a4d384`는 겹침·폭 무제한이었다. 근거 `docs/plans/2026-10-26/tasks-a-judge/`)*
  - **편집:** 편집한 *원래 파일* 줄 범위가 span과 겹치면 겨냥이다. 범위는 `structuredPatch`의 지운 줄(맥락 줄 제외)과 추가한 줄의 삽입 위치(그 앞의 원래 줄)를 **모두 포함한 최소~최대 줄**이다(삭제·삽입이 섞인 패치도 같다). 구조화 결과가 없으면 `originalFile` 안 `oldString` 위치, 그다음 결과 텍스트 스니펫 줄 번호로 대체한다. Edit 결과 텍스트에는 줄 번호가 없다(스모크 실측). 순수 삽입을 범위로 넣는 이유: P2 layered 정답(호출 1줄 추가)·C2(기능 추가)처럼 삽입이 정답인 과제에서 적중이 늘 거짓이 되지 않게 하기 위해서다.

- **첫 편집 적중** *(개정 2, 사용자 결정 2026-10-26 "Bash 편집도 인식" — 근거 `docs/plans/2026-10-26/tasks-redesign/`)*: **기존 파일을 고친 첫 편집 호출**이 정답 위치(symbols의 고칠 곳)에 닿았나. 편집 호출은 Edit 계열 도구와 **대상 파일을 아는 Bash 쓰기**다. 직전 파일럿 4회는 모두 Bash만 써서(`sed -i`, python heredoc) 개정 1 정의로는 값이 없었다.
  - **Bash 쓰기 대상:** 사본 안 대상으로의 리다이렉트(`>`·`>>`·`&>`)·`tee`·`sed -i`·`perl -i`·`cp`/`mv`/`install` 목적지·heredoc 본문으로 준 `patch`·`git apply`(`+++` 대상)·python 인라인 코드(`-c`·heredoc)의 파일 쓰기(`open(…,'w'|'a'|'x'|'+')`·`write_text`·`shutil.copy*`/`move`·`os.replace`/`rename` — 경로는 리터럴·변수에 대입된 값 전부·함수 인자로 푼다). `/tmp`·`/dev`·HOME·`.log`·`.out`·`--dry-run`·`--check`는 편집이 아니다. heredoc 본문은 셸 명령으로 해석하지 않는다.
  - **작업 위치:** `cd`가 바꾼 작업 위치를 같은 명령의 뒤 조각과 다음 Bash 호출까지 유지해 상대 경로를 푼다(사본 밖으로 나가면 사본 루트로). 위 겨냥 정의의 Bash 읽기(`sed -n`·`cat`·`grep`)도 같다 — 개정 1 구현은 `cd` 뒤 상대 경로를 풀지 못해 파일럿 4회 중 3회에서 첫 겨냥 턴이 비었다.
  - **적중:** Edit 계열은 개정 1 그대로(편집한 원래 줄 범위와 겹침). Bash 쓰기는 줄 범위를 모르므로 **파일 단위**(대상 파일이 symbols의 고칠 곳·edit 범위 파일인가)다. 한 호출이 여러 파일을 쓰면 그중 기존 파일 하나라도 맞으면 적중이다. 어느 수단이었는지(`first_edit_via`)를 함께 기록한다.
  - **새 파일:** 실행 전 사본 파일 목록에 없던 대상은 생성(`created_paths`)이라 첫 편집에서 뺀다(Write 생성과 같다).
  - **모름:** 대상을 정할 수 없는 쓰기(입력 파일을 볼 수 없는 `patch < 파일`, 글롭·명령 치환·변수 대상(`"$F"`), 풀 수 없는 `cd`(변수·`cd -`·`popd`) 뒤의 상대 경로, `xargs`·`find -exec`로 넘긴 `sed`/`perl -i`, 경로를 풀 수 없는 python 쓰기)는 첫 편집 적중의 '첫 편집'으로 세지 않고 `edit_unknown_turns`에 턴을 남긴다. 쓰기였는지도 모르는 호출(스크립트 파일 실행 `python x.py`, 쓰기 흔적만 있는 다른 인터프리터 코드)도 같은 목록에 남는다. 분석에서 이 턴이 첫 편집 턴보다 앞선 실행은 표시한다. 편집 수단과 무관한 "첫 편집 턴"(생성 포함)은 따로 기록한다 — 대상을 모르는 쓰기는 포함하고, 쓰기였는지도 모르는 호출은 뺀다. 서브셸 `( … )`·`sh -c` 안의 `cd`는 바깥 작업 위치를 바꾸지 않는다. 풀 수 없는 작업 위치는 절대 경로 `cd`가 나올 때까지 다음 호출에도 이어진다. `if`·`case` 갈래 안의 쓰기는 실행 여부를 모르므로 대상만 남기고 그 턴을 '모름'에 남긴다(오류로 끝난 호출과 같다). 주석(`#`)은 따옴표 밖만 주석으로 본다. 오류로 끝난 Bash 호출의 쓰기 대상은 `edited_paths`에 남기되 실행 여부를 모르므로 첫 편집으로 확정하지 않고 그 턴을 '모름'에 남긴다.
  - **고칠 곳 범위** *(개정 2 명시)*: symbols의 `fix` 범위는 정답 패치 hunk의 원래 쪽 범위로, 문맥 3줄을 포함한다(과제 A부터의 규칙 — 과제·구조 공통). 그래서 고칠 줄 바로 옆을 읽거나 고쳐도 겨냥·적중으로 센다.
  - **누락 대조:** Bash 해석은 휴리스틱이라, 실행 뒤 사본에서 실제로 바뀐 파일(diff) 중 편집으로 인식하지 못한 파일을 `missed_edit_paths`로 남긴다. 값이 있는 실행은 편집 지표를 해석할 때 표시한다.
  - **해석 주의:** 적중(`first_edit_hit`)은 Edit 계열도 Bash도 `edit` 범위(정답 파일 전체)를 포함해 사실상 **파일 단위**다. 고칠 곳이 한 파일에 모인 god(`Marketplace.kt`)에서는 오진 경로(T1의 정산 코드 등)를 고쳐도 같은 파일이라 참이 된다. 그래서 구조 비교에는 **`first_edit_hit_fix`**(Edit 계열이 `fix` 범위와 줄 단위로 겹쳤나 — Bash 편집은 줄 범위를 몰라 값 없음)를 쓰고, `first_edit_hit`는 수단별(`first_edit_via`)로 나눈 보조 지표로만 보고한다.
- **읽은 줄 수:** Read 도구 결과의 줄 수 합(+ Grep·Bash 출력 줄 수 따로). god는 큰 파일 Read 1회의 비용이 크다 — 토큰 차이의 기전을 설명하는 데 쓴다.
- 보조: 턴 수, 도구 호출 수(도구별), 첫 편집 턴, 하위 에이전트 수, 명목 비용, 실행 시간.
- **턴** *(개정 1)* = 본 대화 assistant 메시지 id 수(API 호출 수 — 앞 실험과 같다). CLI `result.num_turns`는 병렬 도구 호출을 따로 세어 다를 수 있다(스모크 실측: 3 vs 4). 둘 다 기록하고 지표는 message.id 기준이다.
- **하위 에이전트**의 읽은 줄은 `sub`로 따로 센다 — 분석에서 합산 여부를 표에 밝힌다.

### 5.3 통계

- 과제마다 r = median(layered) ÷ median(god)(3회 중앙값). 모델별 요약 = 과제 r의 기하평균, 95% 구간 = 과제 안에서 회차를 복원 추출하는 부트스트랩 2,000회(시드 고정). 유형별은 점추정만.
- 정답률은 과제 × 구조의 성공 수/3을 나란히 보고(검정 없음 — 표본이 작다).
- 사전 기준(§1)은 기하평균 **점추정**에 적용하고, 95% 구간이 기준선(0.8·1)을 포함하면 "불확실"을 붙인다. 부트스트랩은 과제 안 회차만 재표집하므로 과제 간 분산은 반영하지 않는다(한계로 표시).
- 요약에는 모든 수정 과제를 넣되, 구조 차이가 의도되거나 처치 효과로 표시된 과제(C2·T2·P2)를 뺀 요약도 같이 낸다. 질문 과제는 토큰만 요약에 넣고 점수는 따로. *(개정 1: 1차 결론에는 질문 과제가 없다 — 요약은 수정 과제 6개, 처치 효과 과제를 뺀 요약은 T1·C1·P1 3개.)*
- **상한 도달(censored):** 예산(`--max-budget-usd`)·시간 상한에 걸린 실행은 valid지만 censored로 표시한다. 종료 원인(예산·시간·정상)은 `result` 이벤트 유무와 따로 기록하고, 시간 상한으로 러너가 프로세스를 끝내 `result`가 없으면 그때까지 받은 assistant 이벤트의 usage 합을 부분 토큰으로 남긴다(무효로 빼지 않는다 — §6.4). *(개정 1)* 부분 토큰은 **하한**이다 — 스트림의 assistant usage는 메시지 시작 시점 값이라 output이 최종값의 1~5%뿐이고(스모크 실측, 총합 오차는 1~2%) 진행 중이던 메시지는 빠진다. **주 분석은 부분 토큰 행의 `total_tokens`를 그대로 쓰고 "하한" 꼬리표를 단다.** 구조별 censored·부분 토큰 행 수를 결과 표에 함께 낸다. 완료 실행만 쓴 민감도 분석의 판정이 주 분석과 다르면 주 판정에 "불확실(상한 영향)"을 붙인다(§1 기준 자체는 점추정에 그대로 적용). 이 비교는 **같은 과제 집합**에서 한다 — 민감도 분석에서 빠진 과제("정의 안 됨")가 있으면 주 분석도 그 과제를 뺀 값으로 다시 계산해 비교한다(과제 집합 차이와 상한 영향을 섞지 않게). output 계열만 따로 보는 분석에서는 부분 토큰 행을 뺀다. 패치는 상한에 걸렸어도 그대로 판정한다(상한 전에 완성된 정답은 성공). **주 분석은 censored 포함**(모든 valid 실행 — §1 사전 기준은 이 계열에 적용), censored 제외는 민감도 분석이다. 제외 분석에서 한 구조의 완료 실행이 0회인 과제는 그 과제의 비율을 "정의 안 됨"으로 표시하고 요약 기하평균에서 뺀다(뺀 과제 수를 함께 보고). 상한은 파일럿 p95보다 충분히 높게 다시 정한다.
- 사전 기준 밖의 사후 분석은 "탐색적"으로 표시한다.

### 6.3 호출

### 6.4 무효·재개

- valid = (result 이벤트 있음 ∨ 러너가 시간 상한으로 끝냄) ∧ 감사 위반 없음 ∧ 인프라 정상 ∧ 사용량 한도 아님 *(개정 1: ∧ 아래 무효 사유 어느 것도 아님)*. 예산·시간 상한 도달은 valid + censored(§5.3).
- 무효 사유 *(개정 1 — 러너 `classify`·`run_one`)*: `audit` · `network`(프록시 거부) · `harness` · `version_mismatch`(init CLI 버전 ≠ 이미지) · `usage_limit`(한도·과부하 문구 — 시간 상한에 걸렸어도. 근거는 stderr 꼬리와 result·system 이벤트 텍스트뿐이다 — 도구 결과·assistant 본문은 보지 않는다(감사의 "입력만" 원칙과 같게). *과제 A 작업에서 반영 — 그 전 러너 `3a4d384`는 stdout 꼬리 전체를 봤다. 앱 소스에는 해당 문구가 없음을 확인했다(2026-10-26 grep 0건))* · `no_result` · `no_activity`(첫 응답 없이 시간 상한) · `agent_error`(오류 result) · `no_modelusage`(정상 result인데 modelUsage 없음) · `infra`(기동 실패·실행 중 DB/가짜 PG 중지·정리 실패·디스크·러너 예외) · `interrupted`(중단 신호) · `orphan`(러너가 행 없이 죽은 시도 — 다음 실행·cleanup이 기록). 중단 뒤 시작하지 않은 job은 시도가 아니라 행을 만들지 않는다.
- 감사(도구 **입력**만 — 결과까지 보면 오탐): 금지 경로(실험 저장소·oracle·다른 실행), 금지 도구, Bash의 `curl·wget·nc·ssh·gh`·`git clone/fetch/pull`. *(개정 1)* 외부 접속 차단의 정본은 프록시(§6.1)이고 감사는 시도를 드러내는 보조다. Bash는 셸 토큰화로 명령을 나눠 래퍼(`timeout`·`env`·`sudo`…)와 `sh -c`를 벗겨 본다. curl·wget은 목적지가 로컬(localhost·127.0.0.1·db)이나 환경 변수면 허용(앱·가짜 PG 디버깅). nc·telnet은 외부 대상만, rsync·scp는 원격 지정만 잡는다. 편집 도구의 내용 필드는 보지 않는다(코드 문자열 오탐). 공개 원격 저장소 호스트(github.com 등)는 어느 도구 입력에서든 잡는다(실험 저장소가 공개라 가장 현실적인 누출 경로).
- 인프라 무효: DB·가짜 PG 기동 실패, 디스크, 러너 예외 — 출력 꼬리를 행에 남겨 에이전트 오류와 구분.
- 사용량 한도·과부하 오류(구독): 무효 + 대기 뒤 재시도.
- 결과 `runs.jsonl`에 (과제, 구조, 모델, 반복)당 valid 행이 있으면 건너뛰고 무효만 다시 돈다(재개). 무효 수와 사유는 결과 표에 함께 보고한다(무음 제외 금지).

## 9. 타당성 위협

1. **코드가 작다:** god 2.7천·layered 4.8천 줄. 앞 실험(8만 줄)에서도 grep 3턴에 원인 파일에 닿았다 — 이 크기에서는 구조 차이가 작게 나올 수 있다. "차이 없음"은 "이 크기에서"로 한정해 보고한다.
2. **layered가 순수하지 않다:** SQL 동치를 위해 일부 규칙(등급 경계·정산 대상 조건·수수료 floor)을 도메인이 아니라 infra SQL에 두었다(layered 2단계 재합의). C1의 등급 경계가 여기에 해당하나, 적립률은 layered 도메인 1곳이라 고칠 곳은 두 구조 2 대 2로 같다(선검증) — 영향은 "규칙이 도메인에 모여 있지 않다"는 탐색 비용 쪽에 남는다.
3. **layered가 더 길다:** 1.8배. 토큰 비교는 "같은 동작을 다르게 짠 코드"의 비교이지 같은 줄 수의 비교가 아니다.
4. **과제 설계자 편향:** 메인이 두 구조를 다 안다. 주입·변경 지점 선택이 한쪽에 유리할 수 있다 — 과제 리뷰에서 "이 과제가 어느 구조에 유리한가"를 렌즈로 둔다.
5. **채점자 편향:** Opus가 실행 모델이자 채점자 — codex 교차로 점검.
6. **표본:** 과제 8 × 3회 — 구간이 1을 포함하기 쉽다(앞 실험도 그랬다). 사전 기준 밖 해석은 탐색적. *(개정 1: 1차는 6 × 3회·한 모델이라 구간이 더 넓다. 점추정 판정에 '불확실' 꼬리표가 붙는 결과도 정직한 결과로 그대로 보고한다 — §5.3.)*
7. ~~**네트워크는 열려 있다:** API 호출 때문에 컨테이너의 외부 접속을 막지 않는다 — 입력 감사(curl·wget·git clone 등)로만 잡는다.~~ *(개정 1)* **네트워크:** 외부 접속은 프록시 허용 목록으로 차단된다(§6.1). 남은 한계 — 프록시를 거치지 않는 직접 접속 시도는 차단되지만 기록되지 않아 "시도했으나 막힌" 실행이 valid로 남을 수 있다(결과 오염은 없음).
8. **처치 효과로 표시한 비대칭 과제:** C2(고칠 파일 수)·T2(형제 규칙 거리)·P2(재사용 메서드) — 구조 차이 자체가 만든 차이라 처치에 포함하되, 이 과제를 뺀 요약도 낸다. layered 상수 이름(`PENALTIES_TO_RESTRICT`)처럼 주입 뒤 남는 이름 단서는 네이밍(구조의 일부)으로 본다.
9. **기존 회귀가 주입을 못 잡는 과제:** *(개정 2: 새 T1의 주입은 기존 계약 테스트(BatchTest·BuyerActionTest·SettlementTest 등)에 걸린다 — 아래 문장의 T1은 개정 1 정의다.)* T1·P2는 기존 계약 테스트가 주입 상태에서도 통과한다 — 판정이 숨은 테스트 하나에 걸리므로 5회 결정성 검사가 필수(§3.1).
10. **모델 업데이트:** 실행 중 모델이 바뀔 수 있다 — 실행마다 모델 ID 기록, 한 모델의 실행은 몰아서.
11. **1차 결론의 범위** *(개정 1)*: Sonnet 한 모델·수정 과제만이다. 모델에 따른 구조 효과 차이와 읽기 전용 과제의 효과는 1차 결론에 들어가지 않는다. 질문 과제(god 유리 예상)를 뺀 요약이라 사전 등록 요약보다 layered 쪽으로 치우칠 수 있다(§2).
12. **T1 지점 거리** *(개정 2)*: T1의 두 고칠 곳이 layered는 한 클래스 20줄 간격·상수 `CONFIRM_WITHIN` 공유, god는 630줄 간격이다. 주입 뒤 layered `confirmationTime(now)`가 인자를 그대로 돌려주는 흔적 함수로 남는다. 응집의 결과라 처치에 포함하지만, 처치 효과 과제 표시는 하지 않았다(사용자 결정) — T1 결과를 해석할 때 함께 적는다. 또 합류점에서 '확정 시각만' 자르는 오답은 layered에서 더 그럴듯하다 — 두 고칠 곳 사이의 도메인 setter(`Order.markConfirmed`) 하나로 끝나 보이고 포인트 확정은 다른 파일이다(god는 4줄 함수 안에 붙어 있다). 이 함정도 기록만 한다(사용자 결정 2026-10-27). 요약에는 T1을 뺀 값도 탐색적 민감도 분석으로 함께 낸다(판정은 사전 기준대로 T1 포함 값).
13. **C2 잠금** *(개정 2)*: 여러 사이즈의 입찰을 한꺼번에 취소할 때 잠금 순서(판매 쪽 사용자→사이즈, 결제 기한 쪽 사이즈→사용자)가 엇갈려 교착할 수 있다. 숨은 테스트·회귀는 순차라 이를 판별하지 못한다(두 구조 같은 조건).
