## 1. 맥락

1차 결론(2026-10-28)은 두 회차 파일럿이 모두 턴 게이트(구조마다 턴 중앙값 ≥ 10)에 못 미쳐 본 실행 없이 끝났다. 턴 중앙값은 5.5~6이었다. 에이전트는 과제 문장의 낱말로 grep해 2~4턴 안에 고칠 곳에 닿았다(관찰, n=1).

코드는 god 2,692줄·layered 4,756줄로 ADR-0001 목표(구현당 1만 줄)에 못 미친다(ADR-0005 §9 위협 1). 사용자는 다음 결정으로 **① 코드 규모 확장**을 골랐다(2026-10-28, ADR-0005 §7.3이 미리 남긴 후보).

이 ADR이 정하는 것:
- 무엇을 어떻게 더하는가(§2·§4)
- 무엇을 바꾸지 않는가(§3)
- 과제를 어떻게 옮기는가(§5)
- 어떤 순서로 진행하고 언제 멈추는가(§6)

기능별 상세 동작 계약(엔드포인트 응답·오류·경계값)은 이 ADR이 정하지 않는다. 묶음마다 계약 ADR(ADR-0007~)을 먼저 쓰고, 테스트를 그 계약에서 만든다. ADR-0003·0004와 같은 방식이다.

## 2. 결정 요약 (사용자 결정 2026-10-28)

| 항목 | 결정 |
|---|---|
| 방식 | **실제 기능 추가.** 리셀 마켓 도메인에 자연스러운 새 영역을 두 구조에 같은 동작으로 더한다. 채움용 코드·주석·생성 코드는 쓰지 않는다 |
| 낱말 | **겹치게 설계.** 새 기능도 확정·정산·기한·취소·제한·분쟁 같은 기존 과제 개념을 쓴다. 그래서 과제 문장 낱말을 grep하면 결과가 여러 곳으로 퍼진다(§4.2) |
| 크기 기준 | **god 앱 소스 기준.** 최종 목표는 1만 줄 이상이다. `Marketplace.kt` 한 파일이라는 처치 정의는 유지한다. layered는 같은 동작을 레이어로 나눈 만큼 자연스럽게 는다 |
| 진행 | **단계적.** 단계 A(god 약 6천 줄) → T1·C2 파일럿 → 사전 등록 규칙(§6.3)으로 다음을 정한다 |
| 고칠 곳 | **수정 과제 6개의 고칠 곳·읽을 곳은 바꾸지 않는다**(§3의 3). 기존 과제 정답의 본보기가 될 기능은 넣지 않는다(§3의 7) |
| 파일럿 과제 | 기존 T1·C2를 큰 코드로 옮긴다. 같은 주입 의미와 같은 `TASK.md`를 써서 크기만 다른 비교로 만든다(§5) |
| 검증 강도 | 기존과 같은 수준. 기능마다 행동 테스트로 두 구조의 응답·DB를 대조한다. 배치·잠금 경로에는 equiv(SQL·문장 로그)를 둔다 |
| 시드 | **별도 난수·후처리.** 기존 22개 테이블은 바이트 단위로 그대로 둔다. 새 테이블만 별도 난수 스트림으로 만든다(§3의 4) |

## 3. 불변식 (확장 전 과정)

1. **처치 정의 유지.**
   - god: 절차 전체가 `Marketplace.kt` 한 파일이다. 지금처럼 컨트롤러·엔티티·DTO는 `web/`·`entity/`에 둔다. 새 기능의 god 로직도 `Marketplace.kt`에 넣는다.
   - layered: `api·service·domain·infra`로 나눈다. **새 기능 코드는 새 파일에 둔다**(새 서비스·도메인·저장소 클래스).
   - layered의 기존 파일은 다음 세 가지만 바꿀 수 있다: 배치 디스패치 분기 추가(`BatchService.run`의 `when`과 생성자 주입), 컨트롤러 등록, 새 저장소 포트의 import.
   - **개정 1(2026-10-29, 사용자 결정 — ADR-0007 §17의 1):** 새 배치가 기존 키셋 순회·격리를 재사용하도록 셋을 더한다: `BatchTarget` enum 값 추가, `KeysetBatchTargets.spec`의 `when` 분기 추가, `BatchService.kt` `forEachIsolated`의 공개 범위 private → internal. 기존 분기·동작은 바꾸지 않는다. 오류 code는 새로 만들지 않으므로 `Failure` enum·`statusOf`는 바꾸지 않는다(ADR-0007 §2.2).
   - **개정 2(2026-10-30, 사용자 결정 — 해석 명시):** 위의 layered '기존 파일'은 **규모 확장 착수 전에 있던 파일**이다. 기준은 커밋 `95cc1da`(god 단계 A 병합 기록, layered 단계 A 착수 직전)에 이미 있던 `layered/src/main` 파일 55개다. 단계 A에서 생긴 파일(같은 커밋 뒤에 생긴 54개 — 예: `service/ReviewService.kt`·`WishlistService.kt`)은 새 기능 파일이다. 그래서 보충 묶음(§6.1-7)이 그 파일에 메서드·클래스를 더할 수 있다. 기존 파일 허용 목록(위 셋 + 개정 1의 셋)은 그대로다.
   - 묶음마다 두 구조의 과제 파일(§3의 3 대상 파일) 줄 수 변화를 기록한다. god는 `Marketplace.kt`가 커지는 것 자체가 처치이고, layered는 과제 파일이 거의 그대로다. 이 차이가 처치다(§8의 7).
2. **기존 동작 무변경.**
   - 기존 테이블 22개의 스키마·CHECK·FK는 바꾸지 않는다. **새 기능은 기존 테이블을 읽기만 하고 새 테이블에만 쓴다.**
   - 기존 엔드포인트 21개·배치 8개의 요청 경로에 SQL 문장을 더하지 않는다. 배치 디스패치(god `runBatch`, layered `BatchService.run`)에는 새 이름의 분기만 더하고, 기존 분기는 바꾸지 않는다.
   - 확인: 단계마다 기존 행동 테스트 211개, equiv 12개 시나리오, verify 76개 검사를 다시 돌려 그대로 통과해야 한다. 단, verify의 하드코딩 수치 하나(`schema_constraints_present`의 FK 수 34)는 새 FK 수만큼 갱신한다.
   - 예외: 현재 두 앱 모두 참조가 0인 `seller_payout_accounts`는 새 기능이 읽을 수 있다. 쓰기는 새 테이블로 한다.
   - 새 배치도 기존처럼 `/admin/batches` 수동 실행만 한다. 스케줄러는 두지 않는다.
3. **수정 과제의 고칠 곳·읽을 곳 무변경.**
   - 대상은 ADR-0005 §3.2가 정한 수정 과제 6개(T1·T2·C1·C2·P1·P2)의 고칠 곳이다. 이미 만든 T1·C2는 `experiment/oracle/{T1,C2}/symbols.*.txt`의 `fix`·`read` 범위도 포함한다. `edit` 범위(첫 편집 적중용 파일 전체)는 대상이 아니다.
   - 대상 범위의 코드는 의미를 바꾸지 않는다. 줄 번호가 밀리거나 주변에 코드가 추가되는 것은 허용한다.
   - 새 기능은 그 범위의 함수를 **호출만** 할 수 있고, 그 함수 안에 코드를 넣을 수 없다.
4. **시드 결정성.**
   - 기존 22개 테이블의 1k CSV는 확장 전과 바이트 단위로 같다. manifest sha로 대조한다.
   - 새 테이블은 `seedgen.py`의 시뮬레이션(`g.run()`)이 끝난 뒤 후처리 패스로 만든다. 후처리는 기존 `self.rng`를 쓰지 않고 별도 스트림(예: `Random(seed ^ 상수)`)을 쓴다. 입력은 **닫힌 기존 CSV를 다시 읽은 것**이다. 시뮬레이션은 끝난 항목을 메모리에 남기지 않기 때문이다.
   - 새 시드 이미지는 **새 태그**(예: `1k-s42-v2`)로 빌드한다. 기존 `1k-s42` 이미지는 1차 결론 재현용으로 남긴다. 러너(`runner.py` `DB_IMAGE`)·`tools/behavior/run.sh`·equiv의 태그 설정을 함께 바꾼다.
   - 500k는 단계 A에서 다시 빌드하지 않는다. 과제 러너·행동 테스트·equiv는 모두 1k를 쓰고, 500k는 배치 측정(NEXT N1)에만 쓴다. N1을 재개할 때 다시 빌드한다.
5. **낱말 대칭.**
   - 같은 동작을 두 구조에 넣으므로 낱말은 양쪽에 같이 생긴다. 한 구조에만 미끼 주석이나 이름을 두지 않는다.
   - 확인: 기능(A1~A12)마다 §4.2 낱말이 나타나는 코드 위치를 두 구조에서 짝지어 기록한다. 한쪽에만 생긴 항목은 이유를 검토한다(§4.2).
6. **사전 기준 보존.**
   - ADR-0005 §1(토큰 비 판정 기준)과 §7.3 게이트 정의는 바꾸지 않는다.
   - 1차 결론의 파일럿 결과는 새 측정과 섞지 않는다. 별도 사전 등록 단위다.
7. **본보기 배제.** 새 기능은 기존 과제 정답과 같은 모양의 코드를 만들지 않는다.
   - C2: 제한·제재 때 입찰을 일괄 취소하는 코드
   - T1: 기준 시각에 기간을 더한 값으로 **저장 시각을 소급하거나 상한을 두는** 코드(`min(현재, 기준+N일)` 꼴). 새 기능의 기한 판정(기한 안인지·지났는지 비교)은 허용한다. 새 기능이 저장하는 시각(종결·작성·발행 시각 등)은 요청·배치 실행 시각으로 한다.
   - T2·C1: 패널티 계수 경계, 등급 경계·적립률을 다시 구현하는 코드. 판정이 필요하면 기존 저장 상태만 읽는다(예: `sale_restricted_until`).
   - 주석: 이식할 때(§5) 주입·변경되는 규칙을 서술한 주석을 저장소 전체에서 grep해 다시 지운다(ADR-0005 §3.1). 새 코드의 주석도 포함한다.

### 4.2 낱말 겹침 측정

- **대상:** 파일럿 2회차에서 쓰인 검색과 TASK.md의 주요 낱말: `-i confirm`, `-i restrict`, `CANCELLED`, `-i cancel`, `확정`, `정산`, `분쟁`, `7일`, `기한`, `제한`, `settlement`, `dispute`, `confirmedAt|confirmed_at`, `cutoff`.

- **단계 A 끝에 기록할 것:**
  1. 같은 표를 다시 재서 늘어난 배수
  2. 기능마다 낱말이 생긴 위치의 두 구조 짝(§3의 5)
- 기대는 "늘어난다"이지만 문턱은 두지 않는다. 낱말 수는 처치가 아니라 과제 난이도의 기전 변수라 게이트에 쓰지 않는다.

god 1만 줄까지 약 4천 줄을 더한다. 기능 목록은 파일럿 A 결과를 본 뒤 이 ADR을 개정해 정한다. §3 불변식은 그대로 둔다. 게이트 판정 규칙(§6.2)은 바꾸지 않으므로 선택 편향은 기능 선택에만 미친다(§8의 5).

## 5. T1·C2 이식

- `TASK.md`·공개 테스트·숨은 테스트는 그대로 둔다. §3의 3이 이 전제를 지킨다.
- `inject.*.patch`·`fix.*.patch`·`alt-1.*.patch`(T1만)·`naive-*.patch`는 새 기준 코드에 맞춰 줄 위치만 다시 맞춘다. rebase가 의미를 바꾸면 이식이 아니므로 멈추고 보고한다.
- `symbols.*.txt`는 새 줄 번호로 다시 만든다. 새 기능이 과제 규칙을 읽는 곳은 `read`에 넣지 않는다. 과제 정답에 필요한 읽기가 아니기 때문이다.
- 규칙 서술 주석은 저장소 전체를 다시 grep해 지운다(§3의 7).
- **재채택 조건(ADR-0005 §3.1과 같음, 고정 SHA·dirty False에서 실측):**

| 과제 | 상태별 숨은 테스트 결과 | 공통 |
|---|---|---|
| T1(bug) | 과제 시작 상태(주입 후, oracle `none`) 실패 · 정답 5/5 통과 · alt-1 통과 · naive-1~7 실패 | 정답에서 회귀 통과 |
| C2(change) | 과제 시작 상태(변경 전, `none`) 실패 · 정답 5/5 통과 · naive-1~10 실패 | 정답에서 회귀 통과 |

- 회귀에 새 기능 계약 테스트(`contract3`)를 포함한다. 판정기 변경이 필요하다(§6.1의 5).
- 정답이 새 계약 테스트의 기대값을 바꾸면, 갱신할 수 있는 것은 갱신본을 쓰고 아닌 것만 메서드 단위로 사유를 달아 `regression-exclude`에 넣는다(ADR-0005 §3.3).
- `contract3`의 픽스처는 "제한된 판매자 + ACTIVE 입찰" 조합에 기대지 않게 짠다. C2 정답이 그 입찰을 취소하기 때문이다.
- T1 거리 비대칭(위협 12)과 C2 잠금(위협 13)은 줄 수가 바뀌므로 다시 재서 기록한다.

## 8. 타당성 위협 (ADR-0005 §9에 더함)

1. **기능 선택 편향:** 메인이 기능을 골랐고 낱말 겹침을 일부러 늘렸다. 두 구조에 같은 동작으로 넣으므로 처치 대칭은 유지된다. 그러나 "실제 코드베이스에서도 이렇게 겹치는가"는 별문제다. 겹침은 과제를 어렵게 하는 장치로 보고한다.
2. **크기 외 변화:** 새 기능은 기존 테이블에 쓰지 않는다(§3의 2). 그래서 기능끼리 얽힌 실제 코드보다 느슨하게 결합되어 있고, 탐색이 덜 늘 수 있다.
3. **문턱 잡음:** §6.3의 7.5는 실행 2개의 중앙값이다. 우연히 넘거나 못 넘을 수 있다.
4. **크기 비율:** layered ÷ god 비율이 1.77에서 달라질 수 있다(영역별 1.3~2.8, 조사 packet §1.3). 보고에 단계별 줄 수를 함께 쓴다.
5. **단계 B 목록의 사후 선택:** 단계 B 기능은 파일럿 A를 본 뒤 정한다. 게이트 정의는 바꾸지 않지만, 기능 선택이 결과에 영향을 받을 수 있다. 보고에 표시한다.
6. **1만 줄 미달 본 실행:** §6.3 첫 행이면 ADR-0001 목표보다 작은 코드에서 결론을 낸다. "god 약 6천 줄에서"(실측값)로 한정해 보고한다.
7. **god에만 생기는 불연속:**
   - 무엇: `Marketplace.kt`가 약 4천 줄로 커진다(현재 god 전체의 66% 비율로 외삽한 추정). 그러면 ADR-0005 §5.2가 근거로 든 "Read 상한 2,000줄 안"이 깨지고, `cat` 출력 절단도 god에서만 생길 수 있다.
