# ADR-0009: 탐색 위임 측정 — Opus 메인이 탐색을 싼 모델 워커에 맡기면 성공을 잃지 않고 비용이 주는가

- 상태: **제안**(2026-11-03 — 파일럿 전 사용자 합의로 채택) · **[제안]** = 메인이 정한 수치·세부, 채택 때 사용자 확인.
- 앞 결정: [ADR-0005](0005-tasks-judging-runner.md)(러너·판정·무효 처리) · [ADR-0008](0008-search-cost-tasks.md)(과제 S1~S4·채택 수준·fce) · [3차 결론](../results/third-conclusion.md)(§3.3 사후 관찰)
- 근거 기록: `docs/plans/2026-11-03/delegation-measure/`(인터뷰·스모크·리뷰 ledger)
- **사후 선택 표시:** 이 질문은 3차 결론의 사후 관찰(캐시 읽기 75~93%, 찾기 1~3턴)과 사용자 가설에서 나왔다. 아래 기준은 파일럿 전에 고정하지만 질문의 선택은 앞 결과를 본 뒤다(§9의 1).
- **쓰임:** 결론은 claude-code-harness의 워커 위임 규칙(core §5 "워커 위임 기본 Opus·high") 개정의 입력이다. 하네스 개정은 이 결론 뒤 별도 작업이다.

## 1. 맥락

- 하네스는 메인(Opus)이 인터뷰·결정·종합을 맡고, 대량 읽기·탐색은 워커에 맡긴다. 워커 기본 모델은 Opus다.
- 사용자 가설(2026-11-02): 탐색·정리를 Haiku·Sonnet 워커에 맡기고 메인은 그 재료로 결정만 하면 토큰(비용)이 준다.
- 반대 방향의 힘: 워커도 시스템 프롬프트·브리핑을 새로 읽고 요약을 돌려준다(고정 비용), 약한 모델 요약은 놓치거나 지어낼 수 있다(성공 하락), 작은 탐색은 위임이 손해일 수 있다. 1~3차 결론의 과제는 찾기가 1~3턴이라 위임에 불리하다 — 탐색량이 큰 과제를 함께 쓴다(§4).

## 3. 위임 방식

### 3.1 장치 (러너 `--arm`, 커밋 `948e347`)

- `explore-*`는 격리 HOME의 `.claude/agents/explorer.md`에 서브에이전트를 정의한다: 모델 = haiku·sonnet·opus 별칭, 도구 = Bash·Read·Grep·Glob, 본문 = "탐색 전담, 파일을 만들거나 고치지 않는다, 근거(경로·줄 번호)와 요지만 보고". 작업 사본은 바꾸지 않아 판정·diff는 방식과 무관하다.
- `direct`는 종전 실행과 같은 프롬프트·HOME이다(explorer 정의 없음).
- 별칭이 실제로 어떤 모델로 풀렸는지는 `by_model`로 실행마다 기록한다(스모크: opus → `claude-opus-5-5`, haiku → `claude-haiku-5-5`).
- **스모크(가정 1 실증, 2026-11-03):** Opus 메인이 턴 2에 explorer를 1회 호출했고(`subagent_type: explorer`), 서브에이전트 11개 Bash 호출이 모두 `claude-haiku-5-5`로 돌았다. 메인 턴 5·도구 호출 15(sub 포함)·성공(회귀 463 통과)·읽은 줄 sub 1,015 / main 187. 러너 `turns`는 메인 대화만 센다.

### 3.2 프롬프트 접미 (`explore-*`만)

> 탐색 규칙: 고칠 곳 찾기·여러 파일 읽기·호출처 조사 같은 넓은 탐색과 대량 읽기는 Agent 도구로 explorer 서브에이전트에게 맡기고, 그 결과(파일 경로·줄 번호·요지)를 받아라. 결정과 편집은 네가 직접 한다. 편집 전에 explorer 가 가리킨 핵심 1~2곳은 직접 확인하라. grep 한두 번으로 끝나는 작은 조회는 직접 해도 된다.

- `direct`에는 접미가 없다. 접미 자체가 행동을 바꾸는 효과는 `explore-opus`(같은 모델 위임)와 비교해 해석한다(§9의 3).
- 위임 여부는 메인이 정한다. explorer 호출 수(`subagent_calls`)를 실행마다 기록하고, 호출 0인 실행도 표본에 그대로 둔다(의도대로 분석 — 지시의 효과를 잰다).

## 4. 과제

- **S1~S4:** ADR-0008 그대로(고정 SHA experiment/ = `417b3b6`의 판정 자산). 바꾸지 않는다.
- **D1~D3 (새로, 큰 탐색):** 유형별 1개.

| ID | 유형 | 요지(문구는 작성 때 확정) | 탐색이 큰 이유 |
|---|---|---|---|
| D1 | 교차 기능 변경 | 한 규칙을 여러 도메인(5곳 이상, 여러 파일)에 걸쳐 바꾼다 | 적용 지점을 전수로 찾아야 한다 |
| D2 | 원인 추적 버그 | 증상에서 원인까지 호출 경로 3단계 이상을 따라가야 한다 | 증상 자리와 고칠 자리가 멀다 |
| D3 | 조사·보고 후 수정 | 어떤 값·상태를 쓰는 곳을 모두 찾아 일관되게 맞춘다(호출처 전수 조사가 핵심) | 호출처 조사량 |

- **채택(ADR-0008 §4.3 수준):** fix·alt 패치가 두 구조에서 전 단계 통과(×2), fix 숨은 테스트 5회 결정적, none·naive가 숨은 테스트에서 실패(×2, 실패 이름·수가 두 구조 같음), tampered 0. 찾기 비용 조건(과제 낱말 단서)은 걸지 않는다 — 이 ADR의 질문은 찾기 비용이 아니라 탐색량이다.
- **탐색량 조건 [제안]:** 파일럿 `direct`에서 과제마다 두 구조 모두 읽은 줄(`lines_read` 전체 — 메인+sub) ≥ **506**(3차 파일럿 S1~S4 Sonnet 8실행 `lines_read.bash` 중앙값 253의 2배). 못 미치면 그 과제는 "큰 탐색"이 아니다 — 파일럿 게이트(§7).
- 판정 단계·회귀는 ADR-0005 §4.1 그대로(public·hidden·contract·contract2·contract3).

## 5. 지표

### 5.1 주 지표: 실행 명목 총비용

- 값 = CLI 결과 이벤트의 `total_cost_usd`(runs.jsonl `cost_usd`) — 메인과 서브에이전트를 합친 값이다. **스모크 확인(2026-11-03, S1 layered explore-haiku):** 결과 이벤트 `modelUsage`가 모델별 `costUSD`(`costBasis: list`)를 따로 주고(Opus 0.21704460 + Haiku 0.01012519), 합이 `total_cost_usd` 0.22716978과 같다. 분석 도구는 실행마다 이 합 일치를 검사하고, 어긋난 실행은 '모름'으로 보고한다.
- "명목"인 이유: 구독 사용이라 실제 청구액이 아니다. 모델 간 상대 비용의 대리값이다.
- 실패 실행도 비용은 그대로 센다(돈은 들었다). 무효 실행(ADR-0005 §6.4)은 다시 돈다.

### 5.2 비용비와 요약

- 칸 = 과제 × 구조(14칸). 칸마다 r = median(위임 방식 3회 비용) ÷ median(`direct` 3회 비용).
- 요약 R = 14칸 r의 기하평균. 큰 탐색 요약 R_D = D1~D3 6칸의 기하평균, 작은 탐색 요약 R_S = S1~S4 8칸.
- 95% 구간: 칸 안 회차 복원 추출 부트스트랩 2,000회(시드 고정), 방식별.

### 5.3 보조 (판정에 쓰지 않음)

성공 · 총 토큰(모델별) · 메인 모델 토큰 · 벽시계 · 턴 · explorer 호출 수 · 위임 실행 비율 · 읽은 줄(메인/sub) · 첫 정답 편집 턴(fce, S1~S4만 — 정답 범위 있음).

## 6. 성공 비열등

- 위임 방식의 성공 수가 `direct`보다 (14칸 × 3회 = 42실행 합계에서) **1건 넘게 적지 않으면** 비열등. 2건 이상 적으면 열등.
- 과제별 성공 차이는 함께 보고한다(합계 비열등이어도 한 과제에 실패가 몰리면 표시).

## 7. 파일럿·게이트·결과별 할 일 (사전 등록 — 파일럿 실행 전)

### 7.1 파일럿

- 4방식 × 2구조 × D1~D3 × 1회 = **24실행**(`results-del-pilot`). 본 표본에 넣지 않는다.
- **게이트(모두 충족 → 사용자 확인 후 본 실행, 하나라도 미달 → 사용자 결정):**
  1. 24실행 모두 valid(무효는 1회 재실행).
  2. `explore-*` 방식마다 6실행 중 3실행 이상에서 explorer 호출 ≥ 1(지시가 작동).
  3. explorer가 호출된 실행의 `by_model`에 그 explorer 모델 토큰이 따로 잡힘.
  4. 본 실행 예상 비용 ≤ $100: 방식별 파일럿 평균 비용 × 42의 합(작은 탐색 과제는 더 싸므로 위쪽 추정).
  5. D1~D3이 §4 탐색량 조건 충족.
  6. `direct`에서 D마다 성공 ≥ 1/2(두 구조 중).

### 7.2 결과별 할 일 (본 실행 뒤 — 방식마다 위에서부터 처음 맞는 행)

| 결과 | 하네스에서 할 일 |
|---|---|
| R < 0.8 · 비열등 · 구간이 0.8을 넘지 않음 | 탐색 워커 기본 모델을 그 모델로(여러 방식이 맞으면 R이 가장 작은 쪽) |
| 0.8 ≤ R ≤ 1.25, 그런데 R_D < 0.8 · 비열등 | "큰 탐색에만 그 모델 워커 위임" 규칙 |
| R > 1.25 또는 열등 | 그 방식은 쓰지 않는다(현행 유지 — 근거 기록) |
| 그 밖(구간이 문턱을 포함 등) | "불확실" — 현행 유지, 사용자 결정 |

- `explore-opus`가 첫 행에 맞으면 "같은 모델이라도 탐색 분리가 이득"으로 읽어 위임 규칙(무엇을 맡기나)을 바꾸는 근거로 쓴다. 모델 변경 근거로는 쓰지 않는다.
- 결과는 "현행 유지"여도 측정 근거로 기록한다(유지가 기본값이 아니라 결과다).

## 8. 실행 순서·비용

- 순서: 반복(1→3)마다 방식 4개를 돌리고, 방식 순서는 반복마다 회전한다(시간대·캐시 상태가 한 방식에 몰리지 않게). 방식 안에서는 러너의 과제·구조 회전 그대로.
- 러너 `--timeout 1800`(30분): 로그인 파일은 실행 시간 상한 + 10분이 남아야 실행이 시작되는데(creds.wait_fresh), 2700초로는 1시간 단위 갱신 주기에서 대기가 잦다(스모크 1차에서 대기 발생). 스모크 실행은 197초.
- 동시 1실행이라 본 실행 벽시계는 168 × 3~5분 ≈ 9~14시간(추정). 판정 포함.
- 비용: 파일럿 24실행 + 본 168실행, 상한 $100(본 실행) — 파일럿 게이트 4에서 다시 추정.

## 9. 타당성 위협

1. **사후 선택:** 질문은 3차 결론의 사후 관찰에서 나왔다.
2. **과제 표본:** 유형별 1개(D)·S1~S4는 작은 탐색. 결론은 "이 과제 7개에서"로 한정한다.
3. **접미 효과:** `direct`에는 위임 규칙 문장이 없다. 비용 차이에 "문장이 행동을 바꾼 효과"가 섞인다 — `explore-opus`가 부분 대조.
4. **명목 비용:** 구독 사용의 청구액이 아니다. 단가 표가 바뀌면 비가 바뀐다.
5. **캐시:** 캐시 쓰기·읽기는 실행 순서·직전 실행에 영향을 받는다(3차 결론 §3.3). 방식 순서 회전으로 섞지만 없애지 못한다.
6. **위임 미호출:** 지시해도 메인이 위임하지 않으면 방식 간 차이가 줄어든다. 호출 비율을 보고한다.
7. **별칭 해석:** haiku·sonnet·opus 별칭이 실행 기간 중 다른 모델로 풀릴 수 있다 — `by_model`로 확인, 바뀌면 보고.
8. **3회 반복:** 칸마다 3회라 중앙값이 불안정하다 — 구간으로 표시.
9. **메인 모델 하나:** Opus 메인만 잰다. Sonnet 메인에서는 다를 수 있다.
10. **작성자 편향:** 메인(Claude)이 D 과제를 만든다. 탐색량 조건은 파일럿 실측으로 건다.
