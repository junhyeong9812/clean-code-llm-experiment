## 2. 경계·불변식 (필수)

- 테스트는 ADR-0004·0003·0002만 보고 쓴다. 앱 내부 구조에 의존하지 않는다 — HTTP와 DB 테이블만 접점. 앱별 분기 없음.
- 1단계 규칙 유지: 직렬 실행, 스스로 만든 사용자·상품·사이즈만 단언, 배치 `processed` 정확값 단언 금지, 시계는 앞으로만(현재 시계 기준 상대 이동), 오류는 HTTP 상태 + `code` 함께 단언, 금액 기대값은 ADR-0004 금액 표가 정본.
- 1단계 계약(ADR-0003)과 충돌하는 2단계 규칙은 ADR-0004 보완 절에 명시하고 사용자 합의를 받는다(조용한 변경 금지).
- 시드 이미지는 읽기 원본, 실행 컨테이너는 1회용.

## 5. 검증 방법 (필수)

- `./gradlew :behavior-tests:test` 류 컴파일·실행, 2단계 테스트를 따로 돌리는 태스크.
- `tools/behavior/run.sh god`·`layered`(1단계): 18/18·117/117, skip 0, verify 0 그대로.
- 2단계 실행: 두 앱에서 2단계 계약 테스트 전부 red, 실패 원인 분포 기록(구현이 없는데 통과하는 테스트 = 계약을 검증하지 않는 테스트 → 수정).
- 테스트 기반 자체 테스트(가짜 PG 취소 등) green.
- 반증: 2단계 테스트 몇 개를 골라 기대를 깨는 최소 스텁(테스트 소스 밖 임시 서버)으로 실패를 확인 — 응답·DB를 실제로 보는지.
- 금액 테스트 기대값을 ADR-0004 금액 표와 리뷰에서 대조. 표 자체는 ADR-0002 금액 규칙과 verify 수식으로 검산.
- 리뷰: ADR-0004 = 설계 문서 → 설계 선검증 + 듀얼 1패스. 테스트 코드 = 듀얼 리뷰 루프(≤3).

## 6. stakes (필수)

- 판정: **높음** — 이 테스트가 두 구현과 이후 에이전트 과제의 정답 판정 계약(public contract)이고, 환불·정산·포인트 금액을 다룬다. 틀리면 이후 모든 측정이 오염된다.

## 8. load-bearing 가정

1. **현재 스키마로 2단계 절차를 모두 표현할 수 있다**(DDL 변경 없음). 실증: ADR-0004 초안 작성 중 절차마다 쓰는 테이블·열·CHECK 값을 `docker/schema/` 실파일과 대조해 표로 남긴다. 빠진 것이 있으면 멈추고 보고.
2. **2단계도 고정 시계 + 배치 엔드포인트로 결정적이다**(같은 요청 순서 → 같은 행·금액). 주간 정산·월 등급 재산정·소멸이 시드 행까지 처리해도 테스트는 자기 행만 단언할 수 있다. 실증: 테스트 기반 task에서 정산·등급 배치를 1k 시드에 상대 시각으로 돌리는 스모크를 먼저 설계(구현 없는 앱이라 실행은 red — 대신 fixture INSERT와 단언 대상 분리가 성립하는지 DB 조회로 확인).
