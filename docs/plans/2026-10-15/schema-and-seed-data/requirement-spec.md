  - 규모 진행 → **소규모(사용자 1천) 검증 후 본 규모(50만)**, 넘치면 줄여서 보고

## 1. 목표·대상 (필수)

- **대상:** `clean-code-llm-experiment`, 브랜치 `feat/schema-and-seed-data`(main `62e4e5a`에서 분기)
- **산출물:**
  1. `docker/init/02-schema.sql`: ADR-0002 §6의 테이블 19개 DDL(PK·FK·UNIQUE·CHECK·인덱스). `ccle_god`·`ccle_layered`에 같은 스키마.
  2. 합성 데이터 생성기 `tools/seedgen/`: 시드 고정, ADR-0002 절차를 시간순으로 시뮬레이션해 상태가 일관된 CSV를 만든다(입찰→체결→결제→발송·검수→확정→정산, 취소·만료·분쟁·포인트 적립/사용/복구/소멸 포함).
  3. 적재 스크립트: `COPY`로 CSV 적재 → 시퀀스 보정 → `ANALYZE`.
  4. 불변식 검증 SQL `tools/seedgen/verify.sql`: ADR-0002 §6.1의 9개 + 행 수·합계 리포트.
  5. 시드 이미지: 적재된 PGDATA를 담은 `ccle-postgres-seed:<버전>` 이미지 빌드 스크립트, 그 이미지로 실행 컨테이너를 띄우는 스크립트.
  6. 두 앱의 `ddl-auto: validate`가 이 스키마로 통과(엔티티는 아직 없음 — 기동·스모크 green 유지).
- **끝의 정의:** 소규모(예: 사용자 1천)와 본 규모 둘 다 생성→적재→불변식 9개 위반 0건. 시드 이미지에서 컨테이너가 뜨고 두 앱 스모크 green. 생성기·시드·행 수·체크섬만 커밋(CSV·덤프는 git 제외).

## 2. 경계·불변식 (필수)

- 스키마와 금액·상태 규칙은 ADR-0002가 정본. 생성기가 규칙을 바꿔야 하면 멈추고 보고(ADR 개정은 사용자 합의).
- 같은 시드 → 같은 CSV(바이트 동일, 체크섬으로 확인).
- 생성 데이터의 "현재 시각"은 고정(예: 2026-10-01 00:00 KST)하고, 그 시점에 진행 중인 건(ACTIVE 입찰, AWAITING_PAYMENT, 배송 중, 미정산 등)도 포함한다 — 과제가 진행 중 건을 다룰 수 있게.
- 개인정보 없음: 이름·이메일은 생성 규칙(`user000123@example.test` 류), 계좌는 마스킹 가짜값.
- 디스크: 생성·적재 전 여유 공간 검사. 시드 이미지 1개만 유지.

## 5. 검증 방법 (필수)

- 소규모 생성→적재→`verify.sql` 위반 0 → 본 규모 동일.
- 반증 표본: 일부러 깨뜨린 행(금액 1원 틀림, 고아 FK, 이중 체결)을 넣은 사본에서 verify가 각각 잡아내는지(검사 자체의 그린 위장 방지).
- 같은 시드 2회 생성 체크섬 일치.
- record-level: 테이블별 행 수·상태 분포·금액 합 리포트, 표본 주문 몇 건의 원장 추적.
- 시드 이미지로 컨테이너 기동 시간 측정(load-bearing 가정 2), 두 앱 `./gradlew build` green.

## 6. stakes (필수)

- **중간.** 금액·안분·포인트 원장 규칙이 데이터 의미를 정하고, 이후 모든 과제 판정의 토대다. 새 DB라 불가역 위험은 없다. 리뷰: 듀얼 1패스.

## 8. load-bearing 가정

1. 본 규모(입찰 약 1,200만·원장 약 1,200만 행)를 이 PC(가용 메모리 약 10GB, 디스크 여유 약 50GB)에서 생성·적재할 수 있다. 소규모 측정으로 외삽하고, 넘치면 규모를 줄여 보고한다.
2. 시드 이미지에서 컨테이너가 실행당 수 초~수십 초 안에 준비된다.
