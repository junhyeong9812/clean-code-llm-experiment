## 0. 요구사항 원문 (인터뷰 기록)

- 원문: "슬슬 실험 결론을 내고 싶은데, 어떻게 생각해?" → 메인 제안(1차 결론은 Sonnet만, 질문 과제 Q1·Q2를 빼서 6과제 × 2구조 × 3회 = 36회, 결론 한계 사전 명시) → "축소안으로 진행해줘".
- 함께 반영할 결정(이미 사용자 결정·리뷰로 확정된 것 — `docs/plans/2026-10-25/runner-smoke/log.md`):
  - 외부 접속 = `--internal` 실행 네트워크 + 허용 목록 프록시(사용자 결정 2026-10-26)
  - 겨냥 Read = 범위를 전부 덮고 폭 ≤ 400줄(사용자 결정 2026-10-26)
  - Bash 읽기 겨냥(grep -n·sed -n — 2.1.308에 Grep 도구 없음), 첫 편집 적중 = 기존 파일을 고친 첫 Edit 호출
  - 무효 사유 확장, 턴 = message.id(CLI num_turns와 다를 수 있음), 부분 토큰은 하한, 금지 도구, 로그인 파일은 대기만
- 질문: 없음(범위·결정이 모두 사용자 답과 앞 작업 기록으로 정해짐).

## 2. 경계·불변식 (필수)

- 사전 등록 기준(§1 — 비율 < 0.8 효과 · 0.8~1 미미 · ≥ 1 손해, B = god, 기하평균 점추정 적용)은 **바꾸지 않는다**. 결과를 보기 전의 범위 축소만 한다(사후 축소 아님 — 실행 0회 시점).
- 과제 정의(§3.2의 T1·T2·C1·C2·P1·P2)는 바꾸지 않는다. Q1·Q2는 삭제하지 않고 "보류"로 표시한다.
- 러너 쪽 개정은 구현(`experiment/runner/` `3a4d384`)과 일치해야 한다. 문서가 코드보다 앞서거나 다르게 적지 않는다.
- 이 작업은 문서만 바꾼다.

## 5. 검증 방법 (필수)

- 듀얼 1패스(Opus ∥ codex) → 종합 → codex 감사 → post-fix 재점검(설계 문서 상한).
- 렌즈: ① 개정이 구현과 일치하나(file:line) ② 축소가 사전 기준·과제 원칙(유형별 2개 등)을 깨지 않나 ③ 보류 항목의 재개 조건이 분명한가.
- 설계 선검증은 생략한다. 사유: 새 동작 불변식이 없다(이미 구현·리뷰된 결정의 기록과 범위 축소뿐) — log 1행.

## 6. stakes (필수)

- 판정: **높음**. 실험 결론의 범위를 정하는 장기 설계 결정이다(되돌리면 실행 해석이 바뀐다). 산출물이 설계 문서라 리뷰 상한은 듀얼 1패스다.
