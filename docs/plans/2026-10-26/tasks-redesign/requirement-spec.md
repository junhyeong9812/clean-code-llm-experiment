> 산출물 유형: **실행물**(과제·oracle·숨은 테스트·지표 코드) + ADR-0005 개정 기록 — 1차 결론의 측정 장치

## 0. 요구사항 원문 (인터뷰 기록)

- 원문: 직전 작업(`tasks-a-judge`) 파일럿이 4/4 성공했지만 턴 5~6이라 ADR-0005 §7 게이트(구조마다 턴 중앙값 ≥ 10)에 못 미쳤다. 4회 모두 Bash만 써서 편집 기전 지표가 정의되지 않았다. 사용자 결정은 **"과제를 어렵게 다시 설계"**와 **"Bash 편집도 인식"**이고, 이어서 "계속 진행해줘".
- Q/A(인터뷰 2회, 6문항):
  - 범위 → **T1·C2 먼저 → 파일럿**. 통과하면 그 기준으로 과제 B(T2·C1·P1·P2)를 만든다.
  - 난이도 수단 → **네 가지 전부**: 증상과 원인 위치 분리 · 같은 규칙 여러 지점 · 그럴듯한 오진 유도 · 본보기 없는 기능.
  - 다시 미달하면 → **그때 결론**. "이 코드 크기에서는 Sonnet이 두 구조 모두 쉽게 풀어, 구조 효과를 볼 만큼 과제를 어렵게 만들기 어렵다"를 1차 결론으로 쓰고, 규모를 키운 재측정을 다음 결정으로 남긴다.
  - 실행 허용 → **채택 통과 시 파일럿 4회**. 실패 실행을 재실행할 때는 다시 묻는다. 탐색용 추가 실행은 없다.
  - T1·C2 → **유형은 유지하고 내용은 새로**. T1은 bug, C2는 change이며 같은 영역일 필요는 없다. ADR §3.2 표에 개정 기록을 남기고, 이전 버전은 이력으로 둔다.
  - 진행 → **높음 · auto · ff+push(승인)**.

## 1. 목표·대상 (필수)

`clean-code-llm-experiment`에서 다음 셋을 끝낸다.

1. **새 T1(bug)·C2(change).** 네 난이도 수단을 두 구조에 같은 의미로 넣어 다시 만든다. 공개 자산(`TASK.md`·`TYPE`·`test.sh`·공개 테스트)과 oracle(`design.md`·`inject`/`fix` 패치·naive 패치·숨은 테스트·`symbols`·제외 목록)을 갖춘다.
2. **Bash 편집 인식.** `experiment/runner/events.py`가 Bash 쓰기 명령도 편집으로 센다. 대상은 `sed -i`·`perl -i`, python 등의 파일 쓰기, `>`·`>>`·`tee` 리다이렉트, heredoc, `patch`·`git apply`다. `first_edit_tool_turn`·`first_edit_hit`·`edited_paths`가 Edit·Write 도구와 같은 정의로 채워지고, 대상 파일을 모르면 그렇다고 표시한다.
   - *(범위 확장 2026-10-27 00:57, 사용자 결정 "읽기에도 적용")* Bash 읽기(`sed -n`·`cat`·`grep`) 경로도 `cd`로 바뀐 작업 위치를 반영해 푼다(가정 1 스모크에서 4회 중 3회 겨냥·전체 읽기 지표가 비어 있던 원인). 측정만 바뀌고 에이전트 행동은 그대로다.
3. **파일럿 4회와 게이트 판정.** ADR-0005 §3.2(T1·C2 행)·§5.2에 개정 기록을 남긴 뒤 파일럿 4회(T1·C2 × 2구조 × Sonnet × 1)로 §7 게이트를 판정한다.
   - 통과하면 과제 B로 간다(다음 작업).
   - 미달하면 1차 결론 문서화로 간다(다음 작업).

## 2. 경계·불변식 (필수)

- **ADR §3.1 원칙은 그대로다.**
  - 구조 중립: 같은 TASK.md·공개·숨은 테스트를 쓰고, 구조마다 다른 것은 앱 코드·패치·symbols뿐이다.
  - 주입은 같은 의미로 넣는다.
  - 누출 금지: TASK.md·공개 테스트·지원 코드에 원인 위치·규칙 상수·기대값을 쓰지 않는다.
  - 숨은 테스트는 결과를 단언한다.
  - 고칠 곳의 수를 두 구조에서 맞춘다. 구조 차이 때문에 생기는 예외는 표시한다.
  - 규칙 서술 주석은 grep으로 찾아 두 구조 모두에서 지운다.
- **네 난이도 수단을 두 과제 합쳐 모두 쓴다.** 각 수단은 design.md에 구조별 위치와 함께 적는다.
  - **분리:** 증상이 드러나는 진입점(API·배치)과 고칠 곳이 다른 파일·계층에 있다.
  - **여러 지점:** 같은 규칙이 ≥ 2곳에 있어, 일부만 고치면 숨은 테스트가 실패한다. 두 구조의 지점 수는 같다.
  - **오진 유도:** 증상 근처에 의심스럽지만 정상인 코드가 있다. 그것을 고치는 오답은 naive 패치로 두고, 숨은 테스트에서 실패해야 한다.
  - **본보기 없는 기능(C2):** 바로 옆에 복사할 본보기가 없고, 기존 흐름 여러 곳을 엮어야 하는 기능이다.
- **과제 채택 조건**은 직전 작업과 같고, `check` 명령으로 실측한다(code_sha 기록).
  - 주입이나 기준 상태에서 숨은 테스트가 실패한다.
  - 정답 패치에서는 두 구조 각각 5회 전부 통과한다(1회는 회귀 포함 전 단계).
  - naive마다 숨은 테스트가 실패한다. naive에는 **부분 수정**과 **오진 수정**이 반드시 들어간다.
  - 회귀가 통과하고 verify 위반은 0이다(제외 목록 사유 포함).
  - 숨은 테스트가 요구하는 경로가 두 구조에서 실제로 호출된다(Q3-3 — 이번에는 정답 패치에서 호출 경로를 근거로 적는다).
- **Bash 편집 인식은 측정만 바꾼다.**
  - 에이전트 프롬프트·도구·허용 명령은 바꾸지 않는다.
  - 기존 Edit·Write 도구 지표의 값은 그대로다(회귀 테스트로 확인).
  - 편집 적중은 기존 `edit` 범위(파일 단위)와 같은 기준으로 본다.
  - 인식하지 못한 쓰기를 읽기로 세지 않는다. 판별할 수 없으면 `edit_unknown`으로 표시한다.
- **판정·러너 불변식은 유지한다.** `tasks-a-judge`가 만든 판정(테스트 작업 공간·앱 컨테이너 분리·재판정 상한)과 runner-smoke 명세 §2를 그대로 지킨다.
- **사전 기준은 불변이다.** ADR §1(판정 기준)·§7 게이트는 바꾸지 않는다. 바뀌는 것은 §3.2의 과제 정의(T1·C2 행)뿐이다. 이전 정의와 이전 파일럿 결과(`results-pilot`, 커밋 `5131584`)는 개정 이력으로 남기고, 본 표본에 넣지 않는다.

## 4. 금지영역 (필수)

- `god/`·`layered/` 원본 소스는 수정하지 않는다. 주입·정답은 패치로만 둔다.
- `behavior-tests/`·`tools/`·`docker/`·ADR-0001~0004는 수정하지 않는다.
- ADR-0005는 §3.2 T1·C2 행, §5.2 편집 지표 문단, 개정 이력만 고친다.
- 에이전트(claude) 실행은 채택 통과 뒤 파일럿 4회뿐이다. 탐색용 실행이나 실패 실행 재실행은 다시 묻는다. 과제 검증은 패치와 check로만 한다.
- 판정 코드(`judge.py`·`judge-stage.sh`)는 과제에 필요한 최소 변경만 한다. 변경하면 채택 재실측 전체를 다시 돈다.
- study-note에 쓰지 않는다. main에서 직접 작업하지 않는다. push는 사용자 확인 뒤에 한다.

## 5. 검증 방법 (필수)

- **과제 채택 조건:** §2의 조건을 `check`로 실측하고, 최종 코드 SHA 하나로 고정한 행만 쓴다. 범위는 정답 5회 × 2구조, none/inject, naive 전부다.
- **난이도 수단 점검(실행 전, 문서):** design.md의 네 수단 표를 설계 선검증에서 확인한다. 기준은 "두 구조에 같은 의미로 있는가"와 "한쪽에만 단서가 있지 않은가"다.
- **Bash 편집 인식:**
  - 단위 테스트: 명령 유형별 + 오탐 방지. 예를 들어 `sed -n`·`grep >/dev/null`·`2>&1`·`/tmp`·로그 리다이렉트는 편집이 아니다.
  - 실데이터: 직전 파일럿 4개 이벤트에서 편집 턴·대상 파일을 손으로 확인한 값과 맞는다(T1 두 구조 sed -i, C2 두 구조 python heredoc).
  - 기존 테스트 296개가 통과한다.
- **blind 테스트 워커:** Bash 편집 인식 계약을 명세만 보고 테스트한다(구현 diff는 보지 않는다).
- **파일럿:** ADR §7 게이트를 판정하고 비용·시간·censored·편집 지표 정의 여부를 보고한다.
- **리뷰:** 듀얼 리뷰 루프(≤ 3). 렌즈에 과제 공정성(한쪽 구조 유리)·누출·오진 naive의 실효성을 넣는다.

## 8. load-bearing 가정

1. 직전 파일럿 이벤트의 Bash 명령 문자열만으로 쓰기 대상 파일을 판별할 수 있다(sed -i 경로, python `open(p,'w')`/`write_text` 경로, 리다이렉트 대상). 착수 직후 4개 이벤트에 시제품 파서를 돌려 실증한다. 판별할 수 없는 비율이 높으면 대안으로 넘어가기 전에 보고한다. 대안은 실행 뒤 diff의 파일 목록을 편집 대상으로 쓰고 턴은 명령으로 정하는 방식이다.
2. 이 코드 크기(구현당 2.7k~4.8k줄)에서도 네 수단으로 Sonnet의 탐색 턴을 ≥ 10으로 늘릴 수 있다. 이 가정은 파일럿에서만 실증할 수 있다(탐색 실행 없음 — 사용자 결정). 틀리면 결론으로 간다.
