- Q/A:
  - 묶음 분할 → **12개 한 번에**(ADR 하나 — 스키마·시드 후처리·1k 새 태그 이미지를 한 번만 만든다).
  - 상세도 → **기존과 같은 수준**(ADR-0003·0004처럼 요청·응답 필드, 오류 코드·문구, 경계값, 배치 대상 조건·잠금, 테스트 기대값 정본이 될 예시).
  - 수치(등급 문턱·리베이트율·SLA 일수 등) → **Claude가 제안하고 리뷰에서 확인**(기존 도메인 값과 겹치지 않게, 완료 보고에 목록으로 제시).
  - 새 테이블 시드 → **1k 규모에 비례해 채움**(후처리 패스로 기존 행에서 파생, verify 검사 추가).

- 재합의(조사 결과 뒤, 2026-10-29 — ADR-0006 §3의 1 허용 목록과 부딪힌 2건, spec §4 '멈추고 보고'에 따라 사용자 결정):
  - 오류 code → **기존 code만 재사용**(새 code 없음 — layered `Failure` enum·`statusOf` 무변경).
  - 새 배치 → **허용 목록 개정**(ADR-0006 §3의 1에 `BatchTarget` enum 값 추가·`KeysetBatchTargets.spec` 분기 추가·`forEachIsolated` 공개 범위 private→internal을 더한다. ADR-0006 개정은 이 작업에서 함께 한다).

## 1. 목표·대상 (필수)

`docs/adr/0007-stage-a-contract.md`가 생겨, 구현자가 그것만 보고 contract3 행동 테스트·DDL·시드 후처리·두 앱 구현을 시작할 수 있으면 끝. 담을 것: A1~A12의 엔드포인트(요청·응답·오류), 새 테이블 DDL 수준의 컬럼·CHECK·FK·인덱스, 배치 대상 조건·잠금·격리·응답, 시각 규칙, 금액·시각 예시(테스트 정본), 시드 후처리 규칙(행 수·파생 방식·verify 검사), 기존 ADR 보완 사항. ADR-0006(§3의 1 허용 목록 개정 포함)·README·NEXT와 정합.

## 2. 경계·불변식 (필수)

- ADR-0006 §3 불변식 1~7 전부 준수: 처치 정의(god 로직 `Marketplace.kt`·layered 새 파일), 기존 22테이블·21엔드포인트·8배치 무변경(기존 테이블 읽기만), 수정 과제 고칠 곳·읽을 곳 무변경, 시드 결정성(별도 RNG·기존 CSV 바이트 동일), 낱말 대칭, 사전 기준 보존, 본보기 배제(C2 일괄 입찰 취소·T1 저장 시각 소급/상한·T2/C1 규칙 재구현 금지).
- 새 계약은 기존 공통 규칙(오류 형식·인증 헤더·시각 주입·배치 응답 `{"processed","failed"}`·건별 격리)을 따른다 — 새 공통 규칙은 만들지 않는 것이 기본, 필요하면 근거와 함께 명시.
- 두 구조 동치 가능해야 한다: 같은 SQL로 구현할 수 있는 계약(정렬·페이지·잠금 순서를 명시).

## 5. 검증 방법 (필수)

- 사실 대조: ADR이 인용하는 기존 테이블·컬럼·상태값·오류 코드·고칠 곳 범위는 실파일에서 확인(워커 packet은 핵심 1~2개 메인 교차 확인).
- 설계 선검증: 신설 동작 불변식(기능별 계약·본보기 배제·고칠 곳 비접촉) 덩어리 점검 — 특히 symbols `fix`·`read` 범위 함수에 코드가 들어갈 여지가 없는지.
- 듀얼 1패스(Opus 워커 ∥ codex) — 렌즈: 테스트 가능성(기대값 유일)·두 구조 동치 가능성·ADR-0006 §3 위반·기존 계약과 충돌·누락(오류·경계·잠금·시드) → 종합 → 감사 → post-fix 재점검 1회.

## 6. stakes (필수)

- 판정: **높음** — public 계약(새 API·DB 스키마)이자 실험 타당성(본보기 배제·고칠 곳 비접촉)을 좌우한다. 산출물 유형이 설계 문서라 리뷰 상한 = 설계 선검증 + 듀얼 1패스(core §4 분기).

## 8. load-bearing 가정

1. A1~A12 모두 기존 테이블을 읽기만 하고 새 테이블에만 써서 정의할 수 있다(ADR-0006 조사 packet 근거) — 계약 작성 중 깨지면 그 기능을 빼거나 바꾸고 보고.
