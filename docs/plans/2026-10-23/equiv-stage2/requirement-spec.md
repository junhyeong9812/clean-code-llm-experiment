## 1. 목표·대상 (필수)

`tools/equiv/scenarios/`에 2단계 시나리오 4개(`ful`·`refund`·`s2batch`·`settle`)를 추가해, `tools/equiv/run.sh all`이 현재 HEAD의 god·layered에 대해 **기존 7개 + 새 4개 전부 4층(응답·새 행·Hibernate SQL·DB 문장) 비교**를 하고 결과를 낸다. 완료 조건:

- 새 4개 시나리오가 2단계 API·배치 전 경로를 지나간다(아래 §5 커버리지 표의 각 항목이 응답 또는 SQL 층에 실제로 나타남).
- 반대 순서 3곳 각각에 대해 layered 임시 변이(SQL 순서를 바꾸는 변경)가 해당 시나리오에서 **exit 1 + sql·pgstmt 층 차이**로 잡힌다.
- 결과가 "같음"이면 R1-3 판정을 실측으로 닫는다. "차이 있음"이면 차이 파일·원인 위치를 log와 NEXT에 남긴다(수정은 별도 작업).

## 2. 경계·불변식 (필수)

- **판정의 정직성(기존 하네스 불변식 승계):** 비교가 실제로 일어나지 않았는데 통과로 끝나는 경로가 없다. 새 시나리오도 기존 `call`·`dump`·`app_end`·`compare_layers`를 써서 빈 덤프·앱 종료·명령 실패가 exit 2가 된다.
- **정규화는 명시 규칙만:** 기존 규칙(`norm_pg_tx_id`, id 오프셋, 고정 시계 그대로)을 재사용한다. 새 비결정이 관측되면(예: 가짜 PG 취소 거래 id) 이름 붙은 규칙으로만 추가하고 README 목록에 같은 행을 넣는다 — **새 규칙 추가는 재합의 대상**(목록 밖 차이는 전부 실패).
- **시드 행 비교:** 시나리오가 바꾸는 시드 행(정산 대상 항목·패널티 등)은 정렬 덤프의 md5 digest로, 픽스처 행은 오프셋 줄 단위로 비교한다.
- **격리:** 기존과 같은 일회용 1k 시드 DB·포트(15445·18085·15485)·정리 경로. 한 번에 하나만 실행.
- **도구만 바꾼다:** 앱·테스트·스키마·ADR 무변경. 변이 시험의 임시 변경은 작업 트리에서만 하고 반드시 되돌린다(커밋·스태시 금지, 끝나면 `git status` 깨끗함 확인).

## 5. 검증 방법 (필수)

- **커버리지 표(log에 기록):** 경로별로 어느 시나리오의 어떤 응답 줄·SQL이 그 경로를 지나갔는지.
  - ful: 발송 → 입고 → 검수 PASS → 배송 → 구매 확정 / 검수 FAIL(판매자 귀책·패널티) / 분쟁 제기 → 처리(인정·기각) / 상태 오류 409·권한 403
  - refund: 구매자 취소(첫 항목·마지막 항목 배송비) / 발송 기한 초과 배치(판매자 귀책) / 분쟁 인정(적립 회수) / PG 취소 DECLINE·UNAVAILABLE(반영 없음 + 재시도) / 계약 밖 2건(체결가 < 10원, 취소 기록 금액 불일치 → 409)
  - s2batch: 자동 확정 / 포인트 소멸(배분 allocation) / 등급 재산정(+ 적립률 반영)
  - settle: 주간 정산(시드 전체, 패널티 연결, 한 주 = 한 트랜잭션, 재실행 0건) / 정산 조회
- `tools/equiv/run.sh all` 2회 → 둘 다 같은 판정, 층별 파일 수·줄 수 출력(빈 비교 없음). 새 4개는 단독 실행도 1회.
- **변이 실증 3건**(작업 트리 임시 변경 → `LAYERED_JAR` → 해당 시나리오 exit 1 + sql·pgstmt 차이 → 되돌림 → `git status` 깨끗): 검수 PASS, 분쟁 제기, 포인트 소멸·회수. 변이 방법은 log에 기록(예: 엔티티 변경 직후 `flush`로 UPDATE를 INSERT 앞에 내보냄).
- 기존 7개 시나리오 판정 불변 + 금지영역 diff 0 + 정리 확인(`ccle-equiv-*` 컨테이너·앱 프로세스 0).
- 리뷰: stakes 중간 → 듀얼 1패스(Opus 워커 ∥ codex) + 종합 감사 + post-fix 재점검.

## 6. stakes (필수)

## 자율성

- **auto** (사용자 선택)

## load-bearing 가정

1. 2단계 경로는 기존 정규화 규칙(id 오프셋·`norm_pg_tx_id`·고정 시계)만으로 결정적이다 — 첫 시나리오(ful) 작성 직후 두 앱으로 실행해 조기 실증. 깨지면 새 규칙을 재합의.
2. 반대 순서 3곳은 Hibernate가 실제로 같은 문장 순서로 내보내며, 시나리오가 그 경로를 지나가면 변이로 순서를 바꿨을 때 sql·pgstmt 층에서 잡힌다 — 변이 실증 3건이 이 가정의 검증이다.
