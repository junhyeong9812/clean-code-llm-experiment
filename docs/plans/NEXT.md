## 다음 작업 후보 (우선순위순)

### N1. HTTP 행위 테스트 — 우선순위: 높음 · 갓 클래스와 레이어드가 함께 통과해야 할 계약이다

- **왜 다음인가:** README 4단계의 첫 단계다. 두 구현이 같은 동작임을 판정하는 기준이 이 테스트다.
- **발생 가능한 문제 (이번 작업에서 관측한 신호):**
  - 실행 컨테이너는 처음 건드린 테이블 파일을 통째로 복사한다(`trades` 첫 조회 2.4초 → 0.5초, 최대 약 14GB). 테스트마다 컨테이너를 새로 띄우면 첫 쿼리 지연과 디스크 사용이 누적된다(디스크 여유 42GB).
  - 데이터의 현재 시각이 2026-10-01 00:00 KST로 고정돼 있다. 배치(만료·결제 기한·확정·정산)를 실제 시계로 돌리면 데이터와 어긋난다(ADR §8: 시각을 고정해 부르는 관리 엔드포인트).
  - 50만 규모 verify는 83분이다. 테스트 판정에 verify 전체를 쓸 수 없다.
- **방법론 선택지:**

| 방안 | 요지 | 비용 | 실패 모드 | 맞는 조건 |
|------|------|------|----------|----------|
| A | 테스트 픽스처 = 작은 시드(1천 명) 이미지, 테스트 클래스마다 컨테이너 | 컨테이너 기동 약 1.3초 | 대규모에서만 드러나는 성능·인덱스 문제를 놓침 | 동작 계약 판정 |
| B | 50만 이미지 하나를 띄우고 테스트마다 트랜잭션 롤백 | 첫 접근 복사 1회 | 앱이 커밋하는 경로는 롤백이 안 됨 | 읽기 위주 과제 |
| C | 테스트가 필요한 행만 직접 INSERT(빈 스키마) | 픽스처 작성 비용 | 합성 데이터의 상태 분포를 못 씀 | 경계 사례 |

- **권장 대처:** 동작 계약은 A(+경계 사례는 C)로 하고, 50만 이미지는 에이전트 과제 실행에 쓴다. 시드 이미지는 하나만 두는 규칙(R4)과 충돌하므로 1천 명 이미지를 함께 둘지 사용자 결정이 필요하다.
- **착수 전 확인할 것:** 테스트 대상 절차 범위(입찰·체결·결제·취소·포인트·정산 중 어디까지), 시각 고정 방식(Clock 주입 vs 관리 엔드포인트), 시드 이미지 개수 규칙 변경 여부.

### N2. 갓 클래스 구현 — 우선순위: 높음 · N1 테스트를 통과시키는 첫 구현

- **왜 다음인가:** N1에 의존한다. 레이어드 분리의 출발점이다.
- **발생 가능한 문제:** 생성기(`seedgen.py`)가 ADR 규칙의 해석을 이미 코드로 갖고 있다(§9.2 항목 몫 floor + 1원 배분, 적립 기준 등). 앱 구현이 다르게 해석하면 시드 데이터와 앱이 만든 데이터가 섞여 verify가 깨진다. 실측 예: verify 1차 위반 347건 중 190건이 1원 배분 해석 차이였다.
- **권장 대처:** 앱이 만든 데이터에도 `verify.sql`을 돌려 같은 불변식을 통과하는지 본다(작은 시드에서).
