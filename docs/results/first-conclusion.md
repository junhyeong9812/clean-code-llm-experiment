- 날짜: 2026-10-28 · 결정 근거: [ADR-0005](../adr/0005-tasks-judging-runner.md) §7.3 *(개정 2)* · 작업 기록: `docs/plans/2026-10-26/tasks-a-judge/`, `docs/plans/2026-10-26/tasks-redesign/`, `docs/plans/2026-10-28/first-conclusion/`
- 원자료: `experiment/results-pilot/runs.jsonl`(1회차), `experiment/results-pilot2/runs.jsonl`(2회차), 같은 폴더의 `raw/*.jsonl`(에이전트 이벤트). 결과 폴더는 git에 올리지 않는다(`.gitignore`). 실행 수치는 2026-10-28에 두 runs.jsonl·raw에서 다시 뽑았다. 채택 실측 수(60행·17종)는 `experiment/results/checks/checks.jsonl`의 `code_sha` ae6deda 행, 코드 크기·행동 테스트 수·equiv 시나리오 수는 ADR-0005 §1에서 왔다.

## 1. 결론

> **이 코드 크기에서는 Sonnet이 두 구조 모두 쉽게 풀어, 구조 효과를 볼 만큼 과제를 어렵게 만들기 어렵다**

이 문장은 결과를 보기 전에 정해 두었다. 1회차 파일럿이 게이트에 못 미친 뒤 사용자가 결정했다(2026-10-26, ADR-0005 §7.3 개정 2). "2회차도 미달하면 이것을 1차 결론으로 쓴다"는 결정이다. 2회차도 미달해서 이 문장을 그대로 쓴다.

**이 결론이 말하지 않는 것:**
- god와 layered 중 어느 쪽이 LLM에게 나은지는 말하지 않는다. 본 실행(Sonnet 36회)을 하지 않았다. 아래 수치는 파일럿 8회(과제·구조마다 1회)뿐이다. 본 표본이 아니고 n=1이다.
- 사전 등록한 판정(layered ÷ god 토큰 비 < 0.8이면 효과, ADR-0005 §1)은 내리지 않았다. 판정할 표본이 없다.

## 2. 범위

- **모델:** Sonnet(`claude-sonnet-5-5`) 하나. CLI 2.1.308.
- **과제:** 수정 과제 두 개(T1 bug·C2 change)의 파일럿만. 두 과제는 회차마다 정의가 다르다(§3).
- **코드 크기:** god 2,692줄(그중 `Marketplace.kt` 1,772줄), layered 54파일 4,756줄(최대 파일 535줄). ADR-0001의 "구현당 1만 줄" 목표에 못 미친다(ADR-0005 §9 위협 1). 두 구조의 동작이 같은지는 행동 테스트 211개(1단계 계약 122 + 2단계 계약 89 — README 진행 표의 117·82는 각 단계를 마친 시점의 수)와 equiv 12개 시나리오에서 확인했다.
- **추정 대상:** 사전 등록 요약(8과제, 질문 과제 포함)과 다르다. 1차 범위는 개정 1에서 이미 수정 과제 6개로 줄여 두었다(ADR-0005 §2). 이번 결론은 그 범위 안에서도 게이트 판정까지만 간 것이다.

## 3. 게이트와 두 회차 파일럿

**게이트(ADR-0005 §7.3, 사전 기준 — 바꾸지 않았다):** 아래 넷을 모두 채워야 한다.
- 4실행 모두 valid이다.
- 지표가 전부 파싱된다.
- 하나 이상 성공한다.
- **구조마다 턴 중앙값이 10 이상이다.**

턴은 에이전트 응답 메시지(`message.id`) 수다. 과제가 너무 쉬우면 두 구조 모두 몇 턴 만에 끝나 구조 차이가 보이지 않는다. 그래서 이 조건을 두었다.

| 회차 | 날짜 | 과제 정의 | T1 | C2 |
|---|---|---|---|---|
| 1회차 | 2026-10-26 | 개정 1 | 포인트 예약 배분 순서(정렬 키 한 줄 주입) | 판매자 패널티 조회 API 추가(본보기가 가까이 있음) |
| 2회차 | 2026-10-28 | 개정 2 | 구매 확정 시각 상한 제거(두 지점, 증상은 정산·분쟁에서 드러남, 오진 유도 장치 포함) | 제한이 걸릴 때 활성 입찰 취소(본보기 없는 기능, 여러 지점) |

2회차 과제는 난이도 수단 네 가지(분리·여러 지점·오진 유도·본보기 없음)로 다시 만들었다. 두 과제 모두 채택 조건을 고정 코드(`ae6deda`)에서 다시 쟀다. 결과는 60행이다.
- 정답: 구조마다 5/5 통과했다.
- T1 합류점 대안 정답(alt-1): 두 구조 모두 통과했다.
- 기준 상태(정답 적용 전)와 오답 17종(T1 7·C2 10): 모두 숨은 테스트에서 실패했다.

### 3.2 에이전트가 한 일(관찰)

8실행이 거의 같은 순서로 움직였다. 실행된 도구는 **Bash 하나뿐**이다(Read·Edit·Grep 도구 0회, 없는 도구 이름 `bash` 호출 1회는 §3.1).

1. `cat TASK.md test.sh`로 과제와 테스트 방법을 읽고, `find`로 파일 목록을 본다.
2. 관련 코드를 `grep`(일부 실행은 과제 문장의 낱말로 — 1회차 T1 layered는 `fun allocate`처럼 과제 문장에 없는 낱말)하거나 관련 파일을 `cat`한다.
   - 예: 2회차 T1 `grep -n -i "confirm"`, C2 god `grep -n -i "restrict\|fun \|CANCELLED"`(함수 선언 목록도 함께), C2 layered 파일 `cat` 뒤 `grep -rn "restrictIf"`.
3. `sed -n`으로 고칠 곳 주변을 읽는다.
4. `sed -i` 또는 python heredoc 한 번으로 모든 지점을 고친다.
5. 테스트를 돌린다. 8실행 모두 편집 호출 끝에 `bash test.sh 2>&1 | tail`을 이어 붙였다. 1회차 3실행은 그 호출이 120초를 넘어 자동 백그라운드로 넘어갔고, 다음 호출의 `sleep 100`으로 결과를 회수했다.

2회차에는 Bash 편집을 인식하는 지표가 생겼다. 4실행 모두 첫 겨냥 턴은 2였다. 첫 겨냥 턴은 oracle symbols의 범위(고칠 곳과 읽어야 할 곳 전체, ADR-0005 §5.2) 중 하나를 처음 겨냥해 읽은 턴이다. 고칠 곳(`fix` 범위)에 닿은 턴은 구조마다 달랐다(`first_targeted_turn_by_span`). god은 두 과제 모두 턴 2에 모든 고칠 곳을 겨냥했다. layered T1은 두 번째 지점이 턴 3이었다. layered C2는 규칙 지점 둘이 턴 3, 그 주변 고칠 곳이 턴 4였고, 나머지 세 곳(`Bid.kt`·`JpaBidRepositories.kt`·`CancelBidService.kt`)은 턴 2에 파일 전체를 `cat`해 읽었다(겨냥이 아니라 전체 읽기로 센다). 첫 편집 턴은 4~5였고, 첫 편집은 고칠 파일 안이었다(`first_edit_hit` True 4/4). 실행 뒤 diff 대조에서 파서가 놓친 파일은 0이었다.

**난이도 수단과 턴(이번 실행에서 본 것 — n=1, 대조 없음):**
- 2회차 T1 god은 과제 문장의 낱말(`confirm`) 한 번의 grep 결과에 두 확정 지점이 함께 나왔다. layered는 grep 결과가 `head`로 잘려 두 번째 지점을 턴 3의 범위 읽기(`sed -n 295,370p`)로 닿았다.
- 2회차 C2(본보기 없는 기능)는 제한을 거는 코드를 grep으로 찾아 들어갔다. god은 턴 2, layered는 두 번째 grep(`restrictIf`) 뒤 턴 3에 규칙 지점에 닿았다.
- 에이전트는 증상 쪽(정산·분쟁·매칭)을 거치지 않고 규칙 쪽 낱말로 바로 들어갔다. 난이도 수단(분리·오진 유도)의 효과는 대조 실행이 없어 판단하지 않는다.

### 3.3 토큰에 대해

- 총 토큰의 **74.7~91.5%가 캐시 읽기**다.
- 첫 응답의 입력(캐시 읽기+생성, 시스템 프롬프트 등)은 8실행 모두 약 12.2k다. 이 크기를 턴 수만큼 곱한 **단순 추정**은 61k~73k, 총 토큰의 44~72%다. 실제 캐시 읽기의 구성비와 나머지의 출처는 usage 집계만으로 나눌 수 없어 미확인이다.
- 캐시 읽기는 실행마다 크게 다르다. 예: 2회차 C2 god 79,040 · layered 136,734.
- 턴이 적으면 매 턴 같은 앞부분의 비중이 커서, 탐색량 차이가 총 토큰에서 작아 보일 수 있다(가설).
- 두 회차에서 god·layered 토큰의 크기 순서가 뒤집힌다.
  - C2: 1회차는 god이 많고(150,572 > 118,834), 2회차는 layered가 많다(165,724 > 98,924).
  - T1: 1회차는 layered가 많고, 2회차는 god이 많다.
- 실행이 하나씩이라 이 차이를 구조 효과로 읽을 수 없다.

## 4. 남은 측정 장치(다음 결정에서 다시 쓸 수 있는 것)

- **러너:** 컨테이너 격리, 허용 목록 프록시, 이벤트 파싱, 재개 처리.
- **판정 단계와 `check` 명령:** 채택 조건을 자동으로 잰다.
- **과제 T1·C2(개정 2):** 채택이 확정됐다.
- **편집 인식:** Bash 편집과 작업 위치를 인식하고, diff 대조 안전망이 있다.
- **두 구조의 동치 확인:** 행동 테스트 211개, equiv 12개 시나리오(이 범위에서 같음을 확인).

## 6. 알려진 한계

- **지표 정의의 차이:** 1회차 편집 지표(`first_edit_*`)와 첫 겨냥 턴은 Bash 편집·작업 위치(`cd`)를 인식하기 전 정의로 기록됐다. 첫 겨냥 턴은 3/4가 빈 값이다. 표의 턴·토큰·비용은 정의와 상관없다.
- **`--max-budget-usd`:** 실제로 중단시키는지 확인하지 못했다. 두 파일럿 모두 예산 $5에 닿지 않았다.
- **Bash 편집 해석:** 휴리스틱이라 경계 사례가 남아 있을 수 있다. 실행마다 `missed_edit_paths`·`edit_unknown_turns`로 드러나며, 사용자가 잔여 위험으로 수용했다.
