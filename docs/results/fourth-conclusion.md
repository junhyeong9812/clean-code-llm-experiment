## 1. 결론

> **이 과제 7개에서 Opus 메인이 탐색을 Sonnet 워커에 맡기면 Opus 워커에 맡길 때보다 명목 비용이 약 29% 적었고(R 0.71 [0.63, 0.84]), 관측 성공은 42/42로 같아 사전 등록 마진 −0.10에 대해 비열등했다 — 탐색 워커 기본 모델을 Sonnet으로 바꾼다.**
>
> **Opus 워커에 탐색을 맡기는 방식(위임 지시 포함 방식 전체)은 혼자 풀 때보다 명목 비용이 약 1.76배였다(R 1.76 [1.41, 1.89]) — 위임은 비용 손해이며, 컨텍스트 보호 등 다른 이유로만 쓴다.**

이 두 문장은 결과를 보기 전에 정한 결정 표(ADR-0009 §7.2·§7.3)의 행 문구에 실측값만 넣은 것이다. 모델 효과는 §7.2 첫 행("탐색 워커 기본 모델을 그 모델로"), 위임 효과는 §7.3 셋째 행("위임은 비용 손해(컨텍스트 보호 등 다른 이유로만)")이다. Haiku는 "그 밖" 행 — **불확실(현행 유지, 사용자 결정)**이다. 11-05 개정(둘째 행 R_D 미적용)은 세 판정 중 어느 것도 바꾸지 않았다: sonnet은 첫 행이 먼저 맞고, haiku는 둘째 행도 성공 불확실로 맞지 않으며, 위임 효과의 R_D는 1.70이다.

**이 결론이 말하지 않는 것:**
- Haiku가 성공을 잃는다고 말하지 않는다. 실패 2/42는 성공 차 구간 [−0.158, +0.043]이 마진 −0.10에 걸린 "불확실"이지 "열등"이 아니다.
- 성공이 실제로 줄지 않는다고 단정하지 않는다. 42/42 대 42/42의 차 구간 [−0.084, +0.084]는 작은 감소 가능성을 포함한다.
- "위임 자체"가 비용 손해라고 말하지 않는다. 비교 대상은 `explore-opus` ÷ `solo`이고, `solo`는 위임 지시 문장도 없고 Agent가 막혀 있다(위협 3). 사후 계산에서 Haiku 위임은 혼자보다 쌌다(§4의 3).
- 위임이 컨텍스트 보호로 얼마나 값하는지는 재지 않았다. 실행 하나가 과제 하나라 메인 컨텍스트가 넘치는 길이까지 가지 않는다(메인 읽은 줄 수만 보조로 쟀다 — §3.3).
- 다른 메인 모델, 더 큰 코드, 다른 과제, 탐색 외 워커(구현·리뷰·테스트 설계)에도 그런지는 말하지 않는다.
- god와 layered 중 어느 쪽이 나은지는 말하지 않는다(구조는 칸을 나누는 데만 썼다).

## 4. 사후 관찰 (판정에 쓰지 않음 — 사전 등록 밖)

1. **Haiku 실패 2건은 한 칸에 몰렸다.** 둘 다 D3 layered(rep 2·3)다. diff는 지연 기록만 고치고 알림 창은 그대로인 naive-1 형태다. 파일럿에서도 유효 실행 중 실패는 이 칸의 explore-haiku 1건뿐이고 같은 형태였다(`experiment/results-del-pilot`). 이 형태가 탐색 누락인지 문구 해석 차이인지는 결과만으로 가를 수 없다(`experiment/oracle/D3/design.md` DT-6). explorer 보고에 알림 창이 있었는지는 궤적으로 확인하지 않았다. 나머지 13칸은 Haiku도 3/3이다.
2. **Haiku·Sonnet 위임에서 메인의 Opus 비용은 줄었다(0.188 → 0.146·0.143, 약 −23%).** explore-opus는 워커도 Opus라 메인 몫을 나눌 수 없다. 늘어난 비용은 워커 몫이다. Haiku 워커는 실행당 $0.008로 작았고, Sonnet 워커는 $0.078로 메인 절감보다 컸다.
3. **혼자 대비 비(사후 계산 — 같은 도구, 같은 시드):** sonnet ÷ solo R 1.252 [1.041, 1.342](42/42 대 42/42 — 셋째 행 문턱 1.25를 0.002 넘는 경계값), haiku ÷ solo R 0.845 [0.755, 0.935](40/42 대 42/42). 혼자보다 싼 위임은 Haiku뿐이다.
4. **explorer 미호출 7/42(방식마다)는 작은 과제에 몰렸다.** S4가 방식마다 5/6이고, 나머지는 haiku S1 layered 2, sonnet·opus S1 layered 1·S2 layered 1이다. D는 위임 방식 54실행 모두 호출했다. 그래서 S4 칸 비(opus÷solo 1.07·0.85)는 대부분 위임하지 않은 실행끼리의 비교다 — "S4에서 위임 이득이 없다"는 뜻으로 읽을 수 없다.

## 5. 하네스 입력 (claude-code-harness v4.3 — 별도 작업, 높음 stakes)

- §7.2 첫 행 → 하네스의 **탐색 워커(넓은 탐색·대량 읽기) 기본 모델 Opus → Sonnet**. 성공 비열등(첫 행)을 통과한 워커 중 가장 싼 쪽이 Sonnet이다. Haiku는 더 쌌지만 성공 불확실이다.
- 근거가 닿는 범위: 탐색 전용 워커, 메인 Opus, effort 기본값. 구현·리뷰·테스트 설계 워커에는 근거가 없다.
- §7.3 셋째 행 → 위임 범위 문구: Opus 워커 위임은 비용 절감 수단이 아니었다. 위임은 메인 컨텍스트 보호(대량 읽기·넓은 탐색이 메인에 쌓이지 않게)를 위해 쓴다 — **사용자 해석(2026-11-06)**이며, 이 실험은 컨텍스트 보호 효과를 재지 않았다(§1). "위치를 아는 작은 조회는 메인이 직접"은 측정한 위임 지시(ADR §3.2)에 이미 있던 문장을 옮기는 것이다(S4 결과에서 끌어낸 것이 아니다 — §4의 4).
- Haiku: "불확실 — 현행 유지, 사용자 결정". 사용자 결정(2026-11-06): 하네스에 넣지 않는다.
- 압축을 자주 하는 대안(Opus 혼자)은 이 실험에서 재지 않았다.
