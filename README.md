# clean-code-llm-experiment

사람에게 좋은 설계(캡슐화·지엽성·레이어·클린 코드)는 LLM 코딩 에이전트에게도 좋은가를 재는 실험장이다.

## 배경

[graph-nav-experiment](https://github.com/junhyeong9812/graph-nav-experiment)에서 코드 지도는 에이전트의 토큰을 줄이지 못했다. 탐색 비용과 정답률을 정한 것은 코드 자신의 **아키텍처(지엽성)와 네이밍**이었다. 이는 SOLID·클린 코드가 말해 온 것과 생각보다 많이 겹친다.

그런데 그 실험의 모든 변형은 같은 레이어 구조였다. 이 저장소는 구조 자체를 바꿔 본다.

## 질문과 가설

- **질문:** 사람이 읽기 좋은 구조(레이어·캡슐화·도메인 모델)는 LLM 에이전트의 탐색 비용과 정답률에도 도움이 되는가?
- **가설:** LLM은 사람이 쓴 코드와 사람의 분석 기준으로 학습했다. 그러니 사람에게 좋은 추상화가 LLM에게도 유리할 것이다.

## 설계

- **도메인:** 결제·입찰·구매·정산 + 포인트(결제 금액 기반 적립, 결제 시 사용). "결제"라는 하나의 행위의 절차를 정의하고 그 절차를 푸는 코드를 쓴다.
- **두 구조, 같은 동작 (Kotlin · Spring Boot)**
  - `god/`: 갓 클래스. 절차의 시작과 끝을 클래스 1개, 파일 1개에 담는다.
  - `layered/`: `api · service · domain · infra` 계층.
  - 갓 클래스(절차지향)를 먼저 만들고, 그것을 레이어드로 분리하며 도메인을 끌어낸다. 두 모듈은 같은 HTTP 행위 테스트를 통과해야 한다.
- **DB:** 실제 PostgreSQL(같은 PC의 도커). 합성 데이터(사용자 50만, 거래 약 500만)를 CSV로 만들어 적재하고, 데이터 상태까지 검증한다.

결정 기록: [ADR-0001 기본 세팅](docs/adr/0001-base-setup.md) · [ADR-0002 도메인 절차·규칙과 DB 설계](docs/adr/0002-domain-and-database.md) · [ADR-0003 HTTP API 계약 1단계](docs/adr/0003-http-api-stage1.md)

## 실행

```bash
docker compose -f docker/compose.yml up -d     # PostgreSQL 17, 127.0.0.1:15432
./gradlew build                                 # JDK 21, 두 모듈 + 스모크 테스트(DB 접속)
java -jar god/build/libs/god-0.0.1.jar          # :8081
java -jar layered/build/libs/layered-0.0.1.jar  # :8082
curl localhost:8081/actuator/health
```

- 스키마(`docker/schema/`)는 빈 볼륨에서만 init으로 걸린다. 스키마가 바뀌면 `docker compose -f docker/compose.yml down -v` 뒤 다시 올린다.

### 행위 테스트

```bash
tools/behavior/run.sh god        # 1천 명 시드 DB → 가짜 PG → 앱 → infraTest·contractTest → verify.sql → 정리
tools/behavior/run.sh layered
tools/behavior/run.sh god contract2Test   # 2단계 계약(ADR-0004)만
```

- 같은 테스트(`behavior-tests/`)가 두 앱에 돈다. 계약은 ADR-0003, 금액 기대값은 그 §8 표.
- 루트 `./gradlew build`는 행위 테스트를 건너뛴다. 직접 돌릴 때는 `BEHAVIOR_TESTS=1`과 `BASE_URL`·`DB_URL`이 필요하다(run.sh가 넘긴다).

### god·layered 동치 비교

```bash
tools/equiv/run.sh all           # 시나리오 7종 × 응답·새 행·Hibernate SQL·DB 문장 로그 비교(약 11분), 같으면 exit 0
tools/equiv/measure-expiry.sh    # bid-expiry 소요 시간 측정(판정 없음)
```

- 두 앱이 같은 요청 순서에 같은 결과·같은 SQL을 내는지 본다. 정규화 규칙·종료 코드·한계는 [tools/equiv/README.md](tools/equiv/README.md).

### 합성 데이터와 시드 이미지

```bash
python3 tools/seedgen/seedgen.py --users 1000 --out ~/ccle-csv/1k-v2     # CSV 41개 + manifest.json(행 수·sha256), 시드 고정
tools/seedgen/build-image.sh ~/ccle-csv/1k-v2 1k-s42-v2                  # 적재 → 제약 → VACUUM FREEZE → verify.sql(시드 빌드 전용 검사 켜짐) → 이미지
tools/seedgen/run-db.sh 1k-s42-v2 ccle-run-001 15433                     # 실행 1회용 DB, DB_URL 출력
# 같은 태그로 다시 빌드하면 그 태그의 이전 이미지를 지운다 — 기존 디렉터리·태그(1k·1k-s42·500k·500k-s42)에 쓰지 말 것
```

- 시드 이미지는 태그(규모)마다 하나씩 둔다(행동 테스트·equiv·과제 러너용 `1k-s42-v2` — 단계 A 새 테이블 포함, ADR-0007 §14 · 1차 결론 재현용 `1k-s42` · 배치 측정용 `500k-s42`). 현행 `tools/seedgen/verify.sql`은 단계 A 새 테이블을 검사하므로 `1k-s42`·`500k-s42`(새 테이블 없음)에는 그 이미지를 만든 커밋의 verify.sql을 쓴다. 500k를 다시 만들려면 새 CSV부터 다시 생성해야 한다(새 테이블이 빈 CSV로는 시드 빌드 검사가 실패). 이미지 안에는 DB `ccle_seed` 하나만 있다. 실행마다 컨테이너를 따로 띄우고, 앱은 `DB_URL`로 그 컨테이너에 붙는다.
- `verify.sql`은 ADR-0002의 불변식(§6.1·§9)을 검사하고, 위반이 있으면 실패한다.
- 실행 컨테이너는 처음 건드린 테이블 파일을 쓰기층에 통째로 복사한다(최대 약 14GB). 실행이 끝나면 `docker rm -f <이름>`으로 바로 지운다. 규모 실측은 [ADR-0002 §7](docs/adr/0002-domain-and-database.md).

## 1차 결론 (2026-10-28)

> **이 코드 크기에서는 Sonnet이 두 구조 모두 쉽게 풀어, 구조 효과를 볼 만큼 과제를 어렵게 만들기 어렵다**

- **어떻게 나왔나:**
  - 본 실행 전에 파일럿 게이트를 두었다. 구조마다 턴 중앙값이 10 이상이어야 한다는 기준이다.
  - 과제를 두 번 만들어 파일럿을 두 번 돌렸다. 두 번째는 난이도 수단 네 가지(분리·여러 지점·오진 유도·본보기 없음)로 다시 만든 과제다.
  - 두 회차 모두 8실행 전부 성공했지만 턴 중앙값은 5.5~6이었다.
  - 결론 문장은 "2회차도 미달하면 이렇게 결론 낸다"고 결과를 보기 전에 정해 둔 것이다.
- **관찰:**
  - 에이전트(Sonnet)가 실행한 도구는 Bash뿐이다(없는 도구 이름 `bash` 호출 1회 제외). grep·cat으로 관련 코드를 찾고(일부 실행은 과제 문장의 낱말로 검색), 주변을 읽고, 한 번에 편집하고 테스트를 이어 붙이는 순서로 4~5번의 호출 안에 끝냈다.
  - 총 토큰의 74.7~91.5%가 캐시 읽기였다. 구성비는 미확인이다(근거 문서 §3.3).
- **말하지 않는 것:**
  - god와 layered 중 어느 쪽이 나은지는 말하지 않는다. 본 실행(36회)은 하지 않았고, 파일럿은 과제·구조마다 1회뿐이다.
  - 사전 등록한 토큰 비 판정도 내리지 않았다.
- **범위:** Sonnet 한 모델, 수정 과제 T1·C2의 파일럿, 구현당 2.7k~4.8k줄(목표 1만 줄 미달). 사전 등록 요약(8과제)과 다른 추정 대상이다(ADR-0005 §2·§9 위협 11).
- **다음 결정 후보:** ① 코드 규모 확장 ② 사전 기준 개정(결과를 본 뒤의 변경이라 선택 편향 표시) ③ 실험 종료. 아직 고르지 않았다.

수치·근거: [docs/results/first-conclusion.md](docs/results/first-conclusion.md) · 결정 기록: [ADR-0005](docs/adr/0005-tasks-judging-runner.md)

## 2차 결론 (2026-10-30)

> **god 코드를 2,692줄에서 5,678줄로 2.11배 키워도 Sonnet의 턴이 사전 등록한 증가 기준(구조별 중앙값 7.5)에 못 미쳐, 이 방식의 규모 확장으로는 구조 효과를 볼 만큼 과제를 어렵게 만들기 어렵다.**

- **어떻게 나왔나:**
  - 1차 결론 뒤 두 구조에 실제 기능을 더해 코드를 키웠다(god 5,678줄·layered 9,970줄). T1·C2를 큰 코드로 옮겨 다시 채택하고 파일럿 A를 돌렸다.
  - 4실행 모두 성공했지만 턴 중앙값은 god 6.5·layered 6.0이었다(2회차 5.5·5.5). 게이트(≥ 10)에 못 미쳤다.
  - 결론 문장은 "두 구조 모두 7.5 미만이면 이렇게 결론 낸다"고 결과를 보기 전에 정해 둔 것이다(ADR-0006 §6.3). 실측값만 넣었다.
- **사후 관찰(판정에 쓰지 않음):** 테스트 호출이 120초를 넘겨 백그라운드로 넘어가고 결과를 기다리는 턴이 파일럿 A 4실행마다 1회 생겼다(2회차 0/4). 이 대기 턴을 빼면 중앙값은 god 5.5·layered 5.0이다. 에이전트는 여전히 키워드 grep 한 번 뒤 턴 2~3에 고칠 곳에 닿았다.
- **말하지 않는 것:** god와 layered 중 어느 쪽이 나은지는 말하지 않는다. 파일럿은 과제·구조마다 1회뿐이고 본 실행은 없다. 구조 간 토큰·턴 차이는 비교 불가다.
- **범위:** Sonnet 한 모델, T1·C2 파일럿, god 5,678줄·layered 9,970줄(1만 줄 목표 미달 — ADR-0006 §8 위협 6). 기능 선택 편향·크기 외 변화·문턱 잡음(위협 1~3)이 그대로 걸린다.
- **다음 결정 후보:** ① 실험 종료 ② 과제 난이도 수단 재검토 ③ 다른 모델 탐색 ④ 단계 B 확장(§6.3 규칙상 해당 행이 아니라 사전 규칙 변경). ②~④는 결과를 본 뒤의 선택이다. 아직 고르지 않았다.
